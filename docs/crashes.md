# Crashes in the original game

The game's own crashes, what causes them, and what OpenSC4 does about each. Crashes still to look at are listed at the end.

## 0x0096DA20: reopening a closed record

**Seen:** about once in a few hundred parity runs, on A runs (no simulator code of ours) and B runs alike, nearly always while a city loads ([parity.md](parity.md)). Access violation at 0x0096DA20, `inc dword [eax+4]` with EAX = 0, on the main thread.

**Cause.** A packed-file segment (cGZDBSegmentPackedFile, 0x086D4A89) keeps its open records in a multimap from key to record at interface + 0xD4. Its open (0x009701FD, under the segment's lock from OpenRecord 0x009757A0) looks the key up first; if a record is already open and is in memory (type 2, +0x40), the new record shares the old one's buffer {data*, count} at +0x44: the constructor 0x0096D9D1 stores it and increments its count. The crash is that buffer being NULL. A record's buffer only becomes NULL in its Close (0x0096DB72, vtable 0x00AD82E8 + 0xF8), and Close is only called from the segment's CloseRecord and AbortRecord, which then release the map's reference and erase the node. So the node the open found should not exist: most likely its record was destroyed some other way (an extra Release; record counts are plain 16-bit increments with no lock) and the pool slot kept its type, NULL buffer and size. Seen in the one surviving report: an FSH texture (type 0x7AB50E44, group 0x891B0E1A, instance 0x15), size 0x14, the old record in the pool slot next to the new one.

**sc4fix** meant to guard the increment (its "puzzle-piece crash, part 1", 0x0096DA1D to 0x0096DA23) but installs that hook at the wrong address, so it never runs ([patch-census.md](patch-census.md), 3.2). Its guard would also have left the new record with a NULL buffer, which the record's reads dereference.

**Fix:** `resources.stale_record_fix = ours` ([src/core/stale_record_fix.cpp](../src/core/stale_record_fix.cpp), off by default). An entry detour on 0x009701FD: on a read-open, while the key's first map node points at a record that is type 2, has no buffer and is closed (flags word +0x0A zero), the node is erased (0x00927CF8) without touching the record, and the open then reads the record from the file as if it were not open. Each drop is logged (`stale_record_fix:` in opensc4.log). The parity harness turns it on for both runs (`scripts/run-parity.sh`, its base list), so the crash no longer costs a pair, and a drop shows in the run's log. Not fixed: the extra Release behind it, and a node whose freed slot has been reused by another record (nothing to tell it apart).

The sibling constructor 0x0096DA30 has the same unchecked increment at 0x0096DA95, but only when an 8-byte allocation fails.

## Puzzle piece over a transit-enabled lot

**Cause.** A solver in the network tool takes its next entry at 0x0065ED80: a pending (id, value) pair from its stack (+0x50/+0x54), or else the entry of its hash table (+0x28; buckets +0x2C to +0x30, node [0] next, [1] id, [2..8] the entry) with the smallest range hi - lo (node [3] - [2]); a negative range is its failure exit (failing id at +0x10, false). With the table empty, or every range NaN or infinite, it chooses no entry and reads the entry's flags through NULL at 0x0065EE40.

**sc4fix** patches the middle of the function (0x0065EE3E, 0x0065EE66) to jump to the failure exit then, with failing id 0; its second patch only makes that jump safe, and pops an x87 stack that is empty on that path.

**Fix:** `fixes.puzzle_piece = ours` ([src/core/puzzle_piece_fix.cpp](../src/core/puzzle_piece_fix.cpp), off by default). An entry detour checks the same condition before the original runs (no pending pair, and no node whose range is negative or below FLT_MAX, compared in double as the x87 does) and returns the failure itself: nothing changed, failing id 0, false. The one caller (0x00660B10) ignores the outputs on false. It coexists with sc4fix, whose patches sit later in the function.

## Crash on exit with plugin DLLs

**Cause.** At shutdown the game's GZCOM library list frees every plugin DLL (cGZCOMLibrary::Free, 0x0087B3B3, through a FreeLibrary wrapper called at 0x0087B3D1) while their objects or threads can still be reached, and the game then calls into unmapped code. sc4fix NOPs that call.

**Fix:** `fixes.pin_plugin_dlls = ours` ([src/core/pin_plugin_dlls.cpp](../src/core/pin_plugin_dlls.cpp), off by default). Once all plugins have loaded, every module that exports `GZDllGetGZCOMDirector` (but the exe and core.dll) is pinned with `GetModuleHandleEx(GET_MODULE_HANDLE_EX_FLAG_PIN)`, so FreeLibrary leaves it mapped until the process ends. Nothing after the call depends on the unload: Free ignores its result and only clears the handle and its loaded flag. Like sc4fix's NOP, a library the game frees and loads again would keep its static state.

## Prop pox

Not fixed: sc4fix's "vaccine" does not change what the save does. It replaces cSC4COMSerializer::SaveClassObjects (0x005D3DE0, slot 7 of the vtable at 0x00AA268C) with a rewrite, but the original performs the same steps in the same order: per object the size and CRC placeholders, the object ID, Write, then seeks back to fill in the size and a CRC of up to 250,000 bytes (the game's CRC at 0x00932FCF is the same CRC-32: MSB first, polynomial 0x04C11DB7, initial 0xFFFFFFFF, no final xor), seeking back to the start on failure; the class map is copied with the objects AddRef'd and each object released as its node is erased, which the rewrite matches by using the game's own copy. So its effect on prop pox, if any, is not in the save logic.

The load side (LoadClassObjects, 0x005D38D0) is where objects are lost: a CRC mismatch skips the object and stops reading the rest of that class's record; a size that disagrees with what Read consumed is silently realigned; an exception in Read keeps the half-read object; an object ID seen twice makes Read run again on the existing object.

**The prop itself reads back what it writes.** cSC4PropOccupant (ctor 0x005EE050; serializable interface at object + 0xC, vtable 0x00AA484C, class ID 0x2977AA47) writes version 6, the base occupant (0x005E8CD0), its exemplar ID (from the prop type index at 0x00B231A4), two 3-float vectors, six flag bytes, a "has timer" bool with the timer block when set, a uint32 and a byte. Read (0x005EF360) takes the same sequence; the timer block follows the bool stored in the record, and the last byte only exists from version 6 on. Not yet compared: the variants (terrain decal 0x005EE360, burnt building 0x005EF810, automata controller 0x005EFDB0, visual effect 0x005F0210, text decal), the prop manager, and what 0x005EF2E0 returns for an exemplar ID that no longer exists.

**Two defects below the prop, in the save's record code (suspects, not yet shown to fire):**

- *Class streams append.* The stream open (0x005D2410, thiscall(segment, key, bool), RET 0xC) opens an existing record for write before it would create one, and never truncates it. Its bool picks the start: true seeks to 0 (overwrite, the old tail stays if the new data is shorter), false seeks to the record's size (append). SaveClassObjects passes false for every class stream (0x005D3EEA) and true only for the index. If a class record is still in the segment when the save runs, the new objects land after the old ones while the index carries the new count; the loader then reads old objects first, the repeated object IDs run Read twice, and the class's count check fails. DeleteRecord (0x00971A55, packed-file slot +0x98) does nothing, silently, while the key is still in the segment's open map (the same map as the 0x0096DA20 crash), so "delete, then save" can fall through to the append.
- *The 2,000,000-byte spill writes in the wrong place.* An existing record opened for write loads its old data (0x00971178): into memory when compressed (0x00970E67), or when uncompressed into memory or, above 2,000,000 bytes, a temp file `Record_%08x_` (0x00970C4D). The write record (vtable 0x00AD8628: buffer +0x44/+0x48, position +0x50, temp file +0x54, spilled +0x58) writes at 0x00970F0F: when a write would reach 2,000,000 bytes it moves the whole buffer to a temp file and then writes the new data at the file's end, not at the position. That is only right while the position is at the end of the buffer; after a seek back, or over preloaded old data, the new bytes land after the old ones and the old bytes in between stay. The object written at that moment gets a size spanning the stale bytes and a CRC over them, so it passes the load's checks and Read parses stale data. Records of more than 16,000,000 bytes are stored uncompressed (0x0096FF01), which changes which of the two loaders the next save's open takes; both thresholds fit the reports that pox hits big cities.

Neither is reached unless an ordinary save finds the old class records still in the segment; who removes them before SaveClassObjects, and when that is skipped, is not yet known. Next step: log-only detours on the stream open (an append onto a non-empty record), the record write (a spill with the position short of the end), DeleteRecord (refused because the key is open) and LoadClassObjects (each object dropped, by class, ID and reason), run over saves of a big city. If the append fires, the fix is local to the stream and record code: truncate the record when a class stream opens one that exists, and make the spill write at the position.

## Multicore crash

**What players do:** run the game on one core, through Task Manager's affinity or the game's own `-CPUCount:1`. The game's handling of that option (0x0044FC3B in the command-line code) calls 0x005F8CD0, which sets the process affinity to CPUs 0 to N-1; without it the game never sets affinity. Why more cores crash is not established; the game's reference counts are plain increments with no lock (see 0x0096DA20), which threads on two cores can race.

**Fix:** `fixes.single_core = ours` ([src/core/single_core.cpp](../src/core/single_core.cpp), off by default) sets the affinity to one core when core.dll attaches, before the game creates any thread, so it needs no shortcut or command line. The core is `[fixes] core` in opensc4.ini (default: the first core the process may use).

## Out of memory

**Cause.** The Steam exe (1.1.641, Characteristics 0x010F) is not large-address-aware, so the game gets 2 GB of address space; large plugin folders and big cities run out. Players apply the community's 4GB patch, which sets the flag in the exe itself (Steam's file check can undo it).

**Fix:** `opensc4 --large-address` ([src/launcher/mirror.cpp](../src/launcher/mirror.cpp), [src/launcher/pe_patch.cpp](../src/launcher/pe_patch.cpp)). The flag is read when the process is created, so it has to be in the exe that is started. The launcher keeps a mirror of the install in `%LOCALAPPDATA%\opensc4\laa`: every top-level folder but Apps as a directory junction, every top-level file as a hard link (a copy where a link is refused), and an Apps folder of its own with copies of the Apps files (not its subfolders; it has none) and of the exe with the flag set and the checksum recomputed. The install is only read, and no admin rights are needed. The mirror is rebuilt when the exe's size or time changes, and only a folder that is empty or carries the mirror's stamp is ever cleared. The hard links give the install's top-level files a second name (link count 2); with Steam on another drive than `%LOCALAPPDATA%` they cannot be links and are copied (about the install's size, untested). Tested on the Steam install (2026-10-10): every top-level file linked, the mirror takes about 8 MB of its own, Steam's DRM stub accepts the copy, the game finds its data through the junctions, and the process has the full 4 GB (free address space above 0x7FFEB000). core.dll logs the address space at attach (`address space: ... MB`). `OPENSC4_LAUNCHER_ARGS=--large-address` passes it through `run-autotest.sh`.
