# Renderer (P1)

Notes for replacing the game's graphics driver. Build 641, Steam, 2026-10-05.

## How the game gets its driver

- The game talks to graphics hardware only through `cIGZGDriver`, an 80-method interface (83 vtable slots with `cIGZUnknown`; gzcom-dll's [cIGZGDriver.h](../third_party/gzcom-dll/gzcom-dll/include/cIGZGDriver.h) matches the DirectX driver's vtable at 0x00AC4660 slot for slot).
- The graphics system (`cIGZGraphicSystem2`, service 0xC416025C) creates exactly the three stock drivers between core.dll's director `OnStart` and `PreAppInit`: Software 0x7ACA35C6, DirectX 0xBADB6906 and OpenGL 0xC4554841. It makes one current (DirectX here).
- `cSC4App` keeps the requested driver's class ID at offset 0x65C from the object start (`cISC4App` − 0xC, `cIGZApp` − 0x2C), set from the `-d:` option by 0x0044EED0. 0x0044CE40 passes it to `cIGZGraphicSystem2::SetDefaultDriverClassID`.
- **A new class ID is never instantiated.** With the field and `SetDefaultDriverClassID` set to an unknown ID from `OnStart`, the graphics system still created only the three stock drivers and chose DirectX, and never asked core.dll's director for the class. GZCOM sends a director requests only for classes it registered, so nothing else would reach it either. This is why scvk and SCGL take over the OpenGL ID instead.

## Installing our driver: `SetGDriver`

`cIGZGraphicSystem2::SetGDriver(cIGZGDriver*)` sets the current driver object directly. At `PreAppInit` the drivers exist but the game has not set its video mode or loaded anything; a driver made current there receives `SetVideoMode` and everything after it. No class ID is taken (so no collision with scvk, SCGL or render-services' need for the DirectX driver) and nothing is patched.

`renderer.passthrough` ([gdriver_proxy.cpp](../src/core/gdriver_proxy.cpp), registry kind `api`, phase `PreAppInit`) wraps the current driver this way and forwards every call. With it on, a 120 s autotest on a clean install runs the city at the same pace as without it (2015-03-03 and 2015-03-04 at the end) and quits cleanly.

All measurements here are from a clean Steam install (2026-10-05). The first ones were taken on an install whose game folder still had dxwrapper (DirectX 7 to 9), sc4-graphics-options and ReShade; those changed the call volumes several times over (for example about 980,000 `Clear` calls in 120 s instead of 24,515), though not which methods were called.

Not seen through the proxy: calls made before `PreAppInit` (the driver's `Init`, anything the graphics system does while creating drivers). Code that looks a driver up with `GetGDriverByID` gets the original.

## Other driver interfaces

The DirectX driver's `QueryInterface` (0x00882A00) also serves four other interfaces. The OpenGL driver's (0x0087D670) serves the first three and not 0x09CD86F9. The game runs without 0x09CD86F9 but then draws no terrain and no textured models: it is the dynamic vertex buffer interface they draw through ("What the driver calls mean"). So a replacement driver needs the buffer region, snapshot and vertex buffer interfaces; lighting is never queried. Names come from the Mac build's debug symbols (sc4-ghidra-symbols types, where the DirectX driver is `nSGLDX7::cGDriver`), matched by method count, `this` offset and what the Windows code does. The proxy wraps all four with [interface_counter](../src/core/interface_counter.h), which counts calls by vtable slot without needing the signatures.

| IID | Interface | Where | Methods | 120 s run |
|---|---|---|---|---|
| 0x669565FE | `cIGZGBufferRegionExtension` | the driver object (vtable 0x00AC47EC) | 8 (then 7 more of the class's own) | queried once (0x007C3810, kept in 0x00B4E1F0); NewBufferRegion 2, ReadBufferRegion 2,770, DrawBufferRegion 16,600 |
| 0xE69BFE2A | `cIGZGSnapshotExtension` | object + 4 (0x00AC47DC) | 1: `CopyColorBuffer` | queried 2, CopyColorBuffer 1 |
| 0x87E2B87D | `cIGZGDriverLightingExtension` | object + 8 (0x00AC47AC) | 9 | never queried |
| 0x09CD86F9 | dynamic vertex buffers (no Mac name) | separate object held at + 0x1C (vtable 0x00AC4F10) | 9 | queried 225,137 times (0x00593E10, 0x007545C0); slot 3 once per query; slots 6 and 8 407,570 each, 10 404,965, 5 176,675, 7 59,164, 4 15,942 |

- **Buffer regions** (slot: method, Windows DirectX implementation): 3 `BufferRegionEnabled` (true), 4 `NewBufferRegion(buffer)` (0 the render target, i.e. the back buffer the game draws into, 1 and 2 depth surfaces (0x00886750: +0x22C from the device's GetRenderTarget; 1 and 2 are created with DDSCAPS_ZBUFFER); creates an off-screen DirectDraw surface, returns a handle), 5 `DeleteBufferRegion`, 6 `ReadBufferRegion` (7 arguments), 7 `DrawBufferRegion`, 8 `IsBufferRegion`, 9 `CanDoPartialRegionWrites` and 10 `CanDoOffsetReads` (both true). Saving and restoring screen areas, and scrolling the city view (see below).
- **Lighting**: `EnableLighting`, `EnableLight`, `LightModelAmbient`, `LightColor` (two overloads), `LightPosition`, `LightDirection`, `MaterialColor` (two overloads). The Mac order is GCC's; MSVC may order the overloads differently.
- **0x09CD86F9**: dynamic vertex buffers, see "What the driver calls mean". The Mac symbols' interfaces do not match it.

## render-services

[sc4-render-services](https://github.com/caspervg/sc4-render-services) 0.7.1 runs normally in the autotest, and crashes the game as soon as `renderer.passthrough` is on. Its ImGui service gets the current driver (`GetGDriver`), checks `GetGZCLSID() == 0xBADB6906`, then reads a pointer at offset 0x24C of the `cIGZGDriver` pointer: the DirectX driver's internal Direct3D helper (`cISGLDX7D3DX`, which gives it the DirectDraw and Direct3D 7 device), whose `EndScene` it hooks to draw ImGui. The proxy forwards `GetGZCLSID`, so the check passes, and offset 0x24C of the proxy is not that field ([DX7InterfaceHook.cpp](https://github.com/caspervg/sc4-render-services/blob/v0.7.1/src/DX7InterfaceHook.cpp), `CaptureInterface`). Its other services (draw passes, camera, terrain decals) do not touch the driver.

Fix: the proxy copies the DirectX driver's pointer at 0x24C to the same offset in itself, at install and on every `GetGZCLSID` call (render-services calls it right before reading, on every tick). With that, a 60 s run with render-services and the proxy runs normally and quits cleanly (tested on the earlier, modded install). Not verified yet: that its ImGui overlay actually draws (its log, which would say so, goes to the real `Documents\SimCity 4` or to the debugger). If mirroring causes trouble, the fallback is to report a class ID other than DirectX's, which makes render-services skip its overlay.

Testing it: its installer puts `imgui.dll` in the game's `Apps` folder and `SC4RenderServices.dll` in Plugins. Instead, the DLLs were unpacked from the installer with 7-Zip, `SC4RenderServices.dll` went into the test `Plugins` (with `LogToFile=false`: its log otherwise goes to the real `Documents\SimCity 4` whatever `-UserDir` says, and `ShowDemoPanel=true` so ImGui draws every frame), and `imgui.dll` was loaded with `OPENSC4_TEST_PRELOAD`.

## Screenshot harness

[scripts/run-shots.sh](../scripts/run-shots.sh) loads the test city with the simulation paused, saves the frame at each of the 5 zooms and 4 rotations, and quits; [tools/shotdiff.py](../tools/shotdiff.py) compares two output folders and writes diff images (differing pixels in magenta). Building block for step 3: every D3D11 change is checked against the stock DirectX driver this way.

```bash
scripts/run-shots.sh "$B" "$LOCALAPPDATA/opensc4/shots/base"
scripts/run-shots.sh "$B" "$LOCALAPPDATA/opensc4/shots/ours" OPENSC4_REPLACE=renderer.passthrough=ours
python3 tools/shotdiff.py "$LOCALAPPDATA/opensc4/shots/base" "$LOCALAPPDATA/opensc4/shots/ours" \
    --tolerance 32 --max-differing 1.2 --diff-dir "$LOCALAPPDATA/opensc4/shots/diff"
```

[scripts/run-shots-all.sh](../scripts/run-shots-all.sh) does the same for every test city (Making Money, Big City and Rush Hour Tutorials: a small town, a dense downtown, highways) into one folder per city, retries runs that Steam's DRM stub relaunched, and with `--compare <baseline dir>` checks each city against the baseline's folder of the same name. Stock baselines are in `$LOCALAPPDATA/opensc4/shots/stock`. On 2026-10-06 the D3D11 driver matched stock in all 60 shots.

```bash
scripts/run-shots-all.sh "$B" "$LOCALAPPDATA/opensc4/shots/ours" --compare "$LOCALAPPDATA/opensc4/shots/stock" \
    OPENSC4_REPLACE=renderer.d3d11=ours
```

How it works ([autotest.cpp](../src/core/autotest.cpp), `OPENSC4_TEST_SHOTS`):

- **View:** `cISC4View3DWin::SetZoomAndRotation` on the city view (main window → 0x6104489A → 0x9A47B417). The camera starts where the save left it, and the autotest never saves, so every run looks at the same spot. Zooms are 1 (farthest) to 5, rotations 0 to 3. After each change the harness waits 3 s, calls `cISC43DRender::ForceFullRedraw`, waits 1 s more and captures.
- **Capture:** the game's own `cISC43DRender::TakeSnapshot(cIGZString&, bool)` (0x007C2570), which reads the frame through the driver's `cIGZGSnapshotExtension::CopyColorBuffer` and writes a 1024×768 RGBA PNG of the whole window, UI included. A replacement driver must implement that extension for the harness to see its output. Called by vtable slot, see below.
- **Render properties** (`OPENSC4_TEST_RENDER`, by name from `cISC4App::GetRenderProperties`): `RenderAutomata`, `RenderCloudsAndFog` and `RenderWaterEffects` are turned off, because they move in real time. They have to be set at PostAppInit: set just before the city loads, `RenderCloudsAndFog=0` had no effect.
- **Random seeds** (`determinism.fixed_seed`, below).

### Why runs differed, and what is left

| Cause | Effect between two runs | Fix |
|---|---|---|
| Random seeds from the clock | terrain texture variation, flora and wildlife placement: 20-50% of pixels at most zooms | `determinism.fixed_seed` |
| Automata | cars and pedestrians in other places | `RenderAutomata=0` |
| Clouds, water effects | drifting cloud blobs at zoom 1, shimmering coast | `RenderCloudsAndFog=0`, `RenderWaterEffects=0` at PostAppInit |
| Wildlife animation | deer at the same spots in different poses, up to 1.1% of pixels (deltas up to 235) at zooms 3-5 | none: animation runs on real time even while paused |
| Cloud shadows on terrain | a faint drifting patch at zoom 1 (up to 5.7% of pixels, deltas up to 30) | none found; `--tolerance 32` absorbs it |

With all of the above, two runs of the stock driver match each other with `--tolerance 32 --max-differing 1.2`, and so does `renderer.passthrough` against either. As a check that this still catches real changes, a run with `RenderShadows=0` fails 18 of 20 shots (1.1-5.9% of pixels); the two that pass are far zooms where shadows cover about 1% of the frame. So a pass is not proof: look at the diff images when a change is near the limit. A fixed animation clock (P4, fixed stepping) would make the frames exact.

### Fixed random seeds

The game has two random number generators, named from the Mac build's types (`cRZRandom`, `cRZRandomSuper`) by what they do:

- `cRZRandom::Seed` (0x00913667): a 32-bit LCG (`x * 0x41C64E6D + 0x3039`, 0x00913696). Seed 0xFFFFFFFF means `time() ^ clock()`. Its constructor (0x00913A5C) is called from about 80 places, many of them static initialisers that seed from the local time XOR a constant.
- `cRZRandomSuper::Seed` (0x00913A72): a Mersenne Twister; seed 0xFFFFFFFF mixes `time()` and `clock()` (0x00913977).
- The CRT's `rand` is seeded only by Lua's `math.randomseed` (0x008C0B20).

`determinism.fixed_seed` ([fixed_seed.cpp](../src/core/fixed_seed.cpp)) detours both seed functions and gives the n-th call `Mix(base + n)` whatever the game asked for (`OPENSC4_SEED` sets the base). It needs the new registry phase `Attach`, applied from `DllMain`: the launcher injects core.dll while the game's main thread is still suspended, so the hooks are in place before the exe's static initialisers run. Steam's stub does not mind the patched code. The first seeds the game asks for are visibly clock-derived (0x6F615500, 0x2F5DEEBE, 0xCF615537, ...). This is the first piece of P4's "capture RNG"; whether the simulation becomes deterministic with it is still open.

### gzcom-dll: overloaded virtuals are in the wrong order (cISC43DRender only)

MSVC, and clang-cl with it, puts overloaded virtual functions in the vtable in reverse declaration order. gzcom-dll's `cISC43DRender.h` declares `TakeSnapshot(cIGZString&, bool)` before `TakeSnapshot(cIGZBuffer**, bool)`, the order of the exe's slots 22 and 23, so the compiled call to the string overload goes to slot 23, the buffer overload: it would pass a string where a `cIGZBuffer**` is expected. Checked with clang-cl's assembly (`+0x5C` for the string call) against the exe's vtable at 0x00ABAB60 (slot 22 is 0x007C2570, which itself calls slot 23 with a buffer pointer). The autotest calls slot 22 directly. Other overloads in gzcom-dll headers (`StartScreenShake`, `SetBackgroundPicture`, `PickTerrain`, `Pick` here; others elsewhere) may have the same problem; worth reporting upstream once checked. `cIGZGDriver.h` is right: every overload group there (`MakeVertexFormat`, `TexEnv`, `Fog`, `TexStageCombine`, `GetVideoModeInfo`, `SetViewport`) is declared in reverse slot order, as MSVC needs, which the OpenGL and DirectX vtables confirm (for example slot 74 is the rectangle `SetViewport`, `glViewport` plus `glScissor`, and the header declares `SetViewport()` first). So the call counts in "What the game calls" are labelled correctly.

### Draw-call parity

`diagnostics.trace.frames` (with the D3D11 driver) brackets each city frame (`cSC43DRender::Draw`, 0x007CB530) and keeps a checksum of every draw the driver hands its backend: the state the backend reads and the vertices and indices the draw uses, with textures by the checksum of their uploaded pixels (not their handles, which follow load order). With it on, `run-shots.sh` logs the first frame after each shot's full redraw (`autotest: frame zoom z rotation r: draws n hash h`) and waits 60 city frames after the redraw instead of a second. `OPENSC4_FRAME_DUMP=<file>` writes those frames draw by draw (primitive, vertex format, count, first texture, model-view translation, checksum); `OPENSC4_FRAME_DUMP_DRAW=<n>` adds that draw's indices and vertex bytes.

Two runs of the unmodified game do not give the same frames yet (2026-10-09, with fixed seeds, the virtual clock, fixed ticks, agent order and zeroed allocations): textures finish loading in a different order, a few animated objects are at different points of their motion (the number of frames drawn while settling differs, and animation follows the frames), and about 14 terrain vertices in a frame get a different alpha (byte 15 of the 32-byte vertex). So renderer replacements are checked in the same frame against the original instead (compare mode, [architecture.md](architecture.md)), with the screenshots as the end-to-end check.

## The camera

The city view's camera is two objects: `cSC4CameraControl` (0x160 bytes, vtable 0x00ABAD18, code 0x007CB920 to 0x007CE900; zoom, rotation, scrolling, the city's orthographic box) on top of `cS3DCamera` (0x1A8 bytes, vtable 0x00ABD2C4, constructor 0x007FF930, code 0x007FF040 to 0x00800540), the S3D library's camera that `cSC43DRender` creates in its Init (`SC4::operator_new(0x1A8)`). Only the vtables' identity slots are virtual; everything else is called directly.

`cS3DCamera` holds the viewport (+0x8) and an optional sub-viewport (+0x14, +0x18), the orientation (rows of 3 at +0x2C, position +0x50, scale +0x5C) with a version byte (+0x28) and flags (+0x29: 1 moved, 4 rotated), the view built from it (+0x64, rebuilt when +0x98 lags the version), the frustum (+0x184 near, far, left, right, +0x194, +0x198), the projection mode (+0x180: 1 orthographic from `SetFrustum` 0x007FF2E0, 2 perspective), a pixel offset (+0x19C) and depth offset (+0x1A4), and the projection (+0x9C) and its inverse (+0x11C), rebuilt when +0x15C lags the projection version (+0x17C). LookAt (0x007FFD60) builds the orientation from a target and up vector; Project (0x007FFF10), Unproject (0x00800120) and PickRay (0x00800340) go between world and screen.

`renderer.camera.s3d` replaces its 20 functions (all but the constructor, factory and destructor, the identity slots and a few one-instruction getters). The game's callers keep values in ECX and EDX across calls into these functions (the constructor uses ECX after `ResetOrientation`), so each detour is entered through a thunk that saves both. In compare mode every call runs ours on a copy of the camera and the game's on the real one and compares the two cameras, outputs and results bit for bit. A screenshot pass (20 views of the test city, 2026-10-09): 0 divergences in about 2.2 million calls (BuildProjection 378,646, GetView 804,016, PickRay and Unproject 68,086 each, Project 24, every other function at least once; the perspective path of BuildProjection and PickRay was not reached), and with ours on, 20 of 20 screenshots match the game's.

## The camera control

`cSC4CameraControl` (class ID 0xC9C628EC, factory 0x007CCC00, constructor 0x007CC990) turns zoom, rotation and a view centre into the S3D camera's placement. Its fields: the S3D camera (+0xC, referenced), the camera position (+0x10) = the city corner it hangs from for the rotation (+0x1C: (0, 0), (w, 0), (w, d), (0, d)) + an offset (+0x13C), the view centre (+0x44) and an offset to it (+0x50), the target on the camera's axis (+0x38), the view direction and rows (+0x5C, +0x68, +0x74), the plane through the target (+0x80), the target on screen (+0x90, in pixels +0x98; the previous ones at +0xA0), shake pixel offsets (+0xB0), scroll speeds by zoom (+0xB8: 100, 50, 25, 12.5, 6.25), the fine zoom (+0xF0) and zoom limits (+0xF4 0, +0xF8 4, +0xFC 5), the zoom and rotation before, now and after a change (+0x100 to +0x114, saved), the view angle offset (+0x118, -pi/8), pitch (+0x11C), distance (+0x120, 8192), near and far (+0x124), the view size in pixels (+0x12C), metres per pixel and back (+0x134), the bounds polygon (+0x148 on, +0x14C a vector of screen points) and the city size (+0x158).

- The box (0x007CBE40): pixels per tile = the zoom's tile size (0x00ABACE0: 8, 16, 32, 73, 146) x the fine zoom; the pitch by zoom (0x00ABACCC, which camera mods rewrite); near and far from the distance over cos(pitch) and the city's diagonal (at least 4096 m a side); the offset from the angle ((rotation + 1) x pi/2 - pi/8) and pitch.
- The view (0x007CC290): the camera put at the target and aimed at the centre, then shifted by the fraction of a pixel that puts the city corner on a whole pixel (plus the shake), so the picture does not shimmer as the view moves.
- The bounds (0x007CCC60): the view volume's four ground corners (0x007F6BA0) in view units, the sides widened by 500 and the top raised by what the camera sees past the far corners. Moving the centre (scrolling 0x007CD330, after zoom and rotation changes 0x007CD000) clips the move to this polygon (0x007CC650), sliding along the edges it crosses, at most one pass per edge; the centre then goes onto the terrain (or the y = 0 plane).
- Messages: 0xA6B79600 before a zoom or rotation change; after it 0x4A9F2FFE (with the camera control), 0xA6B79601, 0xA6B79602; after a move 0x4A9F2FFE, 0xA6B79611, 0xA6B79612; on setup 0xA6B79620; on a fine zoom change 0xA6B79621. Each but 0x4A9F2FFE carries the old and new zoom and rotation.
- Saved as version 1: the centre and the six zoom and rotation values (`tools/re/save_schemas/camera.py`).

`renderer.camera.control` replaces the 21 functions the rest of the game calls (constructor, destructor, Write, Read, Init, the zoom, rotation, centre, shake, city-size and view-size setters, Scroll, Update, the getters); the class's internal functions are ours behind them. With `[renderer] scale_city = no` ours divides the fine zoom by the render scale while building the box, as the D3D11 driver's wrapper of the game's function does. Compare mode runs ours first without posting messages, puts the object, its S3D camera and its bounds back, runs the game's and compares the two (the S3D camera with its view and projection rebuilt, since the game's run gets them rebuilt by whoever answers its messages); the constructor is compared on a copy, and what cannot run twice (Init, which references the camera, Write, Read, the destructor) runs the game's. Two x87 details matter in degenerate states (a camera far outside the city, where the view turns NaN): `-a + b` must flip the NaN's sign as FCHS does (a compiler turns it into `b - a`), and an addition of two NaNs must use the x87's operand order.

`OPENSC4_TEST_CAMERA_EXERCISE=1` makes the shots harness work the camera before each shot: eight scrolls past the bounds, a rotation, zooms past the maximum, a shake, a centre far outside the city, Update in each mode, fine zoom changes. Results (2026-10-09, 20 views of the test city): with the workout, 0 divergences in about 142,000 calls (Scroll 160, Update 100, SetZoom 41, SetCenter 41, SetZoomFactor 40, SetShake about 141,000 of them, every function at least once; every clipping path reached), screenshots 20 of 20 against the game's with the same workout, 20 of 20 without it, and a save's camera record identical to the game's.

## The terrain

The terrain is drawn by `cSTETerrainView3D` (class ID 0xC9B84E10, constructor 0x007567C0, 0xE8 bytes, code 0x007504F0 to 0x0075CE60, about 166 functions), which `cSTETerrain` creates (0x00749540) and which registers with the 3D render for pass 0 (the land) and pass 2 (water and overlays). A separate overlay manager (0x00735260 to 0x0073CF40) draws decals and shadows on the ground. Nothing in the drawing is random or seasonal; the texture variation comes from a grid of random numbers the terrain simulation fills (0x0074B460).

Each frame, pass 0 (0x0075BFD0, then 0x0075BEE0) works out which rows of the terrain mesh are in view, reloads textures when the terrain type changes, redoes the texture coordinates when the zoom or rotation changes, then draws the land, the city-edge skirts and, when on, the grid. The mesh is two static arrays of 32-byte vertices, land (0x00B4C758) and water (0x00B4C75C): position, BGRA colour at +0xC, texture coordinates at +0x10.

- Rows in view (0x00756750 for the land, 0x00753210 and 0x007539D0 for the water pass): the rows from the camera view's z range, and per row the vertex columns between two frustum edges (line intersections, 0x005D7420), floored and ceiled with the 1.5 * 2^23 trick, clamped, and widened so that each row covers the next. Then each row is kept for land if its highest land vertex reaches the lowest height the camera sees along the row (0x00751EE0, from a plane of the camera view), and for water if its highest water vertex does and is above the lowest land; the row ranges to draw follow.
- Texture coordinates (0x00751C80): planar in x and z, scaled by 0.00175 x (1, 2, 4, 8, 16) by zoom and turned with the camera's rotation.

`renderer.terrain.rows` replaces these (four detours; the helpers are ours behind them). In compare mode ours runs first, the view object and the per-row arrays (or the two vertex arrays) are put back, the game's runs, and the results are compared bit for bit. 2026-10-09, the three test cities with the camera workout: 0 divergences (row updates 661 to 2,271 per run, texture coordinates 25, water rows 21); with ours on, 20 of 20 screenshots match the stock driver's.

### The land pass

The land (0x0075BD10) is drawn twice over the rows in view. First without texture, with each vertex's colour from the terrain record (+0x13; the record is 0x24 bytes per vertex, `cSTETerrain` + 0x6C). Then once per texture layer, blended (source alpha, one), with the colours from +0x10 and each vertex's alpha set to its weight for that layer (three {uint16 id, uint8 weight} at +0x16; 0 when the vertex does not have the layer). The layers come from per-row lists (0x00B4C7E0, rebuilt for dirty rows by 0x0075ABA0) of {layer id, column spans}, sorted by id; the pass draws one layer at a time, in the order the rows in view first show them, with the spans clipped to each row's columns in view. A layer's texture is picked by zoom (0x00B4C670), id and variant (bits 12 to 15). With the driver's dynamic vertex buffers (0x09CD86F9; our driver and the stock one both have them) each layer's strips are copied into a locked buffer with their part of a two-row index template and drawn in one indexed call; without them each row is drawn from the land vertices with the shared row indices (0x00B4C6F4).

`renderer.terrain.land` replaces the pass (the row rebuild and the render context's state calls are still the game's). Its compare mode is the same-frame draw comparison: ours runs first with our D3D11 driver recording a checksum per draw (the state the backend reads, the vertices and indices the draw uses, textures by content) and keeping the draws off the screen (`gd::BeginCapture`); the view, the render context (whose state cache decides which driver calls are made), the S3D camera, the land vertices, the batch globals and the driver's pipeline state are put back; then the game's pass runs and draws, recorded the same way; the draw lists, the driver state and the memory are compared. Frames with rows to rebuild run the game's only (the rebuild frees and allocates list nodes, which a copy cannot undo). `OPENSC4_TERRAIN_SELFCHECK=1` compares the game's pass against itself: 0 divergences in 1,187 passes, so the comparison itself is sound. 2026-10-10, with the camera workout: 0 divergences on the three test cities (1,182, 2,044 and 614 passes, about 6,000 to 12,000 draws each run) through the dynamic buffers, and on the tutorial city through vertex arrays (`OPENSC4_TEST_TERRAIN_ARRAYS=1`, 1,014 passes, about 150,000 draws); with ours on, 20 of 20 screenshots match the stock driver's.

**Row layer lists** (0x0075ABA0, for each row in view whose bit in 0x00B4C7EC is set): the row's list (0x00B4C7E0) is emptied and refilled from the layer ids of the row's vertices and the next row's, one of the three layer slots at a time: a span of columns runs while both rows keep the same id, and goes to that layer's node (0x0075AA60). `renderer.terrain.rowlayers` replaces it (the list's own nodes still come from the game's two helpers); compare mode builds ours, then the game's, and compares the lists and the dirty bit. 2026-10-10, three test cities with the camera workout: 0 divergences (1,157, 1,139 and 1,112 rows); 20 of 20 screenshots with both on.

### The water pass

The water (0x007572A0, pass 2) is drawn when the terrain has water and the tuning shows it: the water colours are refreshed if stale, then the water's faces along the city edges (0x007551C0), then the water surface (0x00752240): the water mesh over the land pass's rows whose water is in view, blended (4, 5), with the zoom's water texture (0x00B4C698), through the dynamic buffers or vertex arrays as the land. The colours (0x00756D20, after a rotation or a terrain change) come per vertex from its depth: a colour from a depth ramp picture (index 0.72 per metre), mixed with a colour picture laid over the city (by its blue channel) or faded to a tint, and an alpha from 0x20 at the surface to opaque at 10 m.

`renderer.terrain.water` replaces the pass, the surface, the colour refresh and the water's edge faces (below), with the land pass's draw comparison plus the water vertices. 2026-10-10, three test cities with the camera workout: 0 divergences (1,240, 2,083 and 658 passes; the colour refresh ran at least 16 times a run); 20 of 20 screenshots with ours on.

### The skirts

The faces along the city edges are two rows of vertices per side, a top row along the terrain (or the water level) and a bottom row: four sides of three textured layers for the land (0x00B4C760, 24-byte vertices, layer textures 0x11, 0x10 and 0x15; drawn by 0x00753E00 for the two sides that face the camera) and four sides for the water (0x00B4C790, 16-byte vertices, untextured, 0x007551C0, all four sides with a depth offset of -1 for the facing sides and -5 for the others, when the water level reaches the terrain's lowest height). For each side the part in view is found by meeting the edge's line with the two frustum edges (as the rows do), mirrored for the sides that run backwards; within it, runs of cells whose top is above their bottom are drawn, each widened by a cell at its start.

`renderer.terrain.skirts` replaces the land's; the water's are part of `renderer.terrain.water`. 2026-10-10, three test cities with the camera workout: 0 divergences (1,207, 1,943 and 653 passes each); 20 of 20 screenshots with ours on.

**Colours** (0x007558B0, when the view's +0x31 is clear): each side gets a grey from its outward normal, turned by the object at 0x00B43DDC (slot 0x5C), and the light vector at 0x00B0D720, scaled by 0x00B0D71C. Top vertices at or above a height (0x00AB43DC) get twice the grey, lower ones a blend down to the grey; each layer's bottom row takes the next layer's top colour and the last layer's the plain grey. `renderer.terrain.skirtcolours` replaces it; compare mode fills ours, then the game's, and compares the twelve vertex arrays. 2026-10-10: 0 divergences in 21 calls per city.

### The grid

The cell lines shown while zoning or building (`cSTETerrainView3D::ShowGrid`, 0x00755E80, sets the byte at 0x00B4C741; the pass is 0x00757650, called after the land's skirts) are the land's vertices drawn once more with the grid texture (the view's +0x88) and blending. The texture coordinates come from a texture matrix built from the camera's (the context's matrix at +0x1AC) on every pass; the vertex alpha, written into the land vertices' colour, fades the lines out towards the water: none below 2 m above the water level, opaque from 4 m, 0.5 per metre between. The rows are drawn by 0x007545C0 (dynamic buffers) or 0x007541C0 (vertex arrays), which the overlay manager also calls with smaller rectangles: the land strips first, then each row's extra quads (0x00B4C6B0, counted per column in 0x00B4C6B8).

`renderer.terrain.grid` replaces the pass. The matrix arithmetic (about 700 x87 instructions without a branch) is translated instruction by instruction by a script, the game's stack frame as an array of cells ([terrain_grid_matrix.inc](../src/core/terrain_grid_matrix.inc)). `OPENSC4_TEST_TERRAIN_GRID=1` shows the grid in test runs. 2026-10-10, three test cities with the camera workout: 0 divergences (1,213, 1,951 and 668 passes each; 1,131 with vertex arrays); 20 of 20 screenshots with ours on against the stock driver with its grid, though the lines are faint enough that the shots also pass against shots without a grid, so the same-frame comparison is the check that counts here.

### The terrain's buffers

Everything the terrain passes draw comes out of a set of buffers the terrain view keeps in globals between 0x00B4C6A0 and 0x00B4C7C0. `STE::BuildBuffers` (0x00758EA0; it runs once when a city is loaded) makes them when they do not exist and fills them; `STE::FreeBuffers` (0x00758750) frees them.

- **Vertices**: land at 0x00B4C758 and water at 0x00B4C75C, 32 bytes a vertex, 0x00B4C754 of them (rows times columns: 0x00B4C750 times 0x00B4C74C, one more than the cells each way). Filled by 0x00752430 (land) and 0x00752520 (water).
- **Index lists**: 0x00B4C6FC (12 bytes a cell of a row), 0x00B4C6F8 and 0x00B4C6B4 (a row's six indices a cell, 0x00B4C700 of them, 16 bits each), 0x00B4C6F4 (the same for every row) and 0x00B4C6B8.
- **Per-row arrays**: 0x00B4C6BC to 0x00B4C6D8 (a byte or a dword a row), and two arrays of 12-byte row records at 0x00B4C6AC and 0x00B4C6B0, each kept as a pointer 4 bytes past a count.

`renderer.terrain.buffers` is the build, the two vertex fills and the free, translated instruction by instruction. Compare mode builds ours and notes every block it allocates with its size; each block is then known by where its pointer is kept, because a build makes some of them anew. The blocks are cleared and the game's builds, twice; the globals and every block must be the same after ours as after the game's, byte for byte, leaving out what differs between the game's own two builds (one global, 0x00B4C7B8, a pointer the water fill gets from another object). A block of ours that nothing points at counts as a difference by itself.

Checked on the three tutorial cities: 33 blocks and the globals, 1,396,028 bytes, no difference; self-checks clean; screenshots with ours alone match the game's (20 of 20 on Big City and Rush Hour), also in the release build with every terrain replacement on. The build runs once a city, so this is one comparison a run, of everything it makes.

The first batch found a bug this way: with ours alone Big City crashed on a jump to a garbage address. The translator had written four bytes where the game writes two (`mov ds:0xb4c6f2,ax`), which cleared half of the pointer after it. The comparison had left that pointer out as one that changes between builds; the block it should have pointed at was the one "nothing points at", which is why that is now a failure.

**Size limits.** Nothing in the build is sized by a constant: every count comes from the terrain's own (0x00B4C744 cells a row and 0x00B4C748 rows, 128 in the tutorial cities). Two things in it are 16 bits wide and so bound a bigger city: the indices (a draw can only reach 65,536 vertices; the passes draw two rows at a time, which is 1,026 vertices for a 512-cell city, so this holds), and the six small counters at 0x00B4C6DC to 0x00B4C6F2. The 256-row limits found for bigger cities (docs/city-size.md) are not here but in the row code: `LandRowThresholds` and `WaterRowThresholds` (0x00751EE0, 0x00751FF0) write one float a row in view into a 257-float buffer on the stack of `LandRowVisibility` and `WaterRowVisibility` (0x007535A0, 0x007539D0). Ours (`renderer.terrain.rows`) has the same 257-float buffer on its stack for standard cities and takes one sized from the terrain's rows when there are more than 257; that path has not run, since no test has a bigger terrain yet.

### The terrain's messages

The terrain view hears about changes through its message handler (0x00757560; `this` is the view + 4). Two messages change the buffers, each for the rectangle of cells the message carries (0x007523F0 reads it):

- **Land changed** (0x278E6003): `UpdateLandHeights` (0x007569F0) copies the heights of the area's vertices from the terrain into the land vertices, and for a vertex on an edge of the city also into that side's skirt (0x00755B60, which keeps the skirt's lower heights from going under their floor).
- **Water changed** (0x678E6E3A): `UpdateWaterHeights` (0x00756B00) sets each vertex's water height in the area (the sea level, or the land plus the water's depth where there is water above it), redoes the four water skirts with their colours, and adds the area to the view's changed rectangle (0x00756000, at +0x4C).

Both mark the view (+0xA8). Two more messages (0x277A9364, 0xC9DA96EA) call slots of the view and set a field.

`renderer.terrain.messages` is the handler and those five functions, translated instruction by instruction. Compare mode (with `renderer.terrain.buffers=compare`, which is what knows the buffers' blocks and sizes) handles each of the two messages twice: ours, then the view, the globals and every block put back, then the game's with the game's own functions, and the results compared byte for byte. The other messages are not run twice.

Checked with the cities running: the three tutorial cities for 30 days, and for land changes a volcano on Big City and an earthquake on Rush Hour for 20 days. 4,741 water messages (308 of which changed something) and 86 land messages (59), no difference; the self-check on the volcano run is clean; ours alone runs the volcano in the release build, and screenshots with every terrain replacement on match the game's (20 of 20). All six functions ran. The seven other messages seen were handled by ours without a comparison.

### The terrain view's draw

The 3D render calls the terrain view's draw (0x0075BFD0) once for each of the view's two passes, with the render context:

- It reads two values from the terrain into the view (+0x64, +0x68), asks for the driver's dynamic buffers (0x0075CD40), sets the depth offset to -3 and the view's render state (the block at 0x00B4C800, set up on the first call), and brings the view matrix up to date.
- When the context's +0x50 is clear it runs **the land's frame** (0x0075BEE0); otherwise the water pass. Then it gives the dynamic buffers back and restores the depth offset. A debug draw (0x00759A80) follows when the byte at 0x00B4BC5C is set, which it never is in the tests.
- The land's frame: the rows brought up to date; the water rows when the view's +0xB8 asks; when the terrain's detail setting differs from the one kept at 0x00B0D6FC, the textures dropped (0x00756CA0) and picked again (0x007571D0); the texture coordinates redone when the zoom (0x007574D0, kept at 0x00B4C70C) or the rotation (0x007566C0, kept at 0x00B4C708) changed; the skirt colours when +0x31 is clear; then the land pass, the land skirts and, when shown, the grid.

`renderer.terrain.viewdraw` is the draw, the land's frame and those four helpers, translated instruction by instruction. Everything they call was ours already, so with this a terrain frame runs from the render's call down to the driver without the game's terrain code, apart from what is listed below.

Compare mode runs the whole draw twice in the same frame, like a pass; the passes under it run the game's own code in both runs, as nested passes always do, so it checks the draw and the land's frame themselves. A frame that brings things up to date (the zoom or the rotation changed, the water rows or the colours are due) loads textures and rebuilds lists and does not come out the same twice even in the game's own code; such frames are counted apart and not repeated. Putting the buffers back between the runs was tried and is not enough.

Checked on the three tutorial cities with the camera workout, and once with the grid shown: 9,526 frames compared, no difference; 21 frames a run are of the kind that is not repeated (one for each change of view), so the two change handlers and the texture pick only run in ours there and are checked by the screenshots. The self-check is clean (3,531 frames). Screenshots with ours match the game's 20 of 20 on Making Money and Rush Hour. On Big City the two farthest views came out at 1.2 to 1.5 % of pixels differing, just over the 1.2 % limit, in the smoke over the industry and nowhere on the terrain; four more runs of those two views gave 0.3 to 1.1 % between any two runs, the game's against the game's included, so this is the particles' run-to-run noise at that zoom.

### Picking

`cSTETerrainView3D::Pick` (0x0075A230) answers where a ray meets the terrain; the tests' camera workout asks it about 3,000 times a run. It first tests the ray against the terrain's box (0x005D6580), then walks the cells along the ray (0x00649820) and tests each cell's two triangles (0x005D6FF0), split along the diagonal the cell's flags give. With its last argument set the cell's corners are raised by the water above them, so the ray meets the water's surface and not the sea bed. While the view's +0x24 is set a hit also marks its cell, which the tests never do.

`renderer.terrain.pick` is that function, translated instruction by instruction. It changes nothing but what its out argument points at, so compare mode simply asks ours and the game's the same question and compares the answers: the result and the point.

Checked on the three tutorial cities with the camera workout and on a running city with a volcano: 9,706 picks, of which 3,370 hit the land and 878 the water's surface, the same answer every time; the self-check is clean, and screenshots after the camera workout with every terrain replacement on match the game's (20 of 20).

### A cell's own texture

A cell can be given a texture of its own (what the passes then draw there is in "The land pass"). The view keeps this by row:

- 0x00B4C6B8: for every row, a 16-bit count for each column and one more: how many cells before that column have a texture of their own. Two neighbouring counts differ where a cell has one.
- 0x00B4C6B0: for every row a vector (begin, end, capacity) of 0x80-byte records, one for each such cell in column order: the cell's four vertices with their colours.
- 0x00B4C6AC: for every row a second vector of 8-byte entries in the same order; the texture is at +4.

`SetCellTexture` (0x00759750: x, z, texture) puts a cell into its row when it is not there yet: the counts after it go up by one, a blank record (0x00755DD0) goes into the record vector (0x00759680, which grows the vector through 0x00758D40) and an entry into the other. Then it sets the entry's texture, fills the record's vertices and colours (0x00756350, 0x007564F0), sets the cell's flag bits 0x60 and redoes the cell's six indices in the row's index list (0x00752AF0). `ClearCellTexture` (0x00758620: x, z) does the opposite. In a running city this happens all the time: about 2,800 sets in 30 days of Big City.

`renderer.terrain.celltexture` is those two and the fourteen helpers under them (the record copies, moves, fills and erases), translated instruction by instruction.

Compare mode has to cope with the vectors moving to new blocks, which rules out simply putting things back. Before ours runs, the row's two vectors are copied into blocks of the same capacity from the game's allocator. After ours, the result is taken (the globals and every buffer block with this row's vector pointers blanked, both vectors' sizes, capacities and contents, the cell's flag byte); everything is put back as it was but with the row's vectors now the copies; ours' vectors are freed; and the game's runs from the same start with its own helpers. It needs `renderer.terrain.buffers` on, which knows the blocks.

Checked with cities running: the three tutorial cities for 30 days and Big City with a volcano for 20: 7,093 sets and 1,265 clears, no difference; the self-check is clean; ours alone with every terrain replacement runs 30 days in the release build, and screenshots match the game's (20 of 20 on Big City and Rush Hour). 15 of the 16 functions ran; the one that fills a run with copies of a record (0x00756690) did not.

### The terrain view's set-up

The first terrain view that starts runs a one-time set-up (0x0075C0C0; the byte at 0x00B4C740 says it has run):

- It registers its own undoing (0x00758BC0) with the framework, to run when the game closes.
- It loads the view's tuning (0x00758990, with a table through 0x00757300) and gets the texture factory (kept at 0x00B4C704).
- It makes five arrays of dwords (0x00B4C670 on), each as long as the size at 0x00B4BC44, and loads the terrain's textures.
- It makes the **row layer lists**: a vector at 0x00B4C7E0 of lists, one a row, which the land pass fills with spans of columns for each texture layer ("Row layer lists" above). And the **dirty row bits** at 0x00B4C7EC, one a row.

The undoing frees the buffers, releases the textures and arrays and clears the byte, so the set-up can run again.

`renderer.terrain.setup` is the set-up, its undoing, the tuning loaders and the seven row layer list helpers a run uses, translated instruction by instruction. `renderer.terrain.rowlists_untested` has seven more helpers of those lists (copies, assignment, erasing a run of nodes) that no test reaches, so that code has never run.

**Big cities.** The game makes 0x100 row layer lists and 0x100 dirty row bits, as literals in the set-up (at 0x0075C36F, 0x0075C37A, 0x0075C3B2 and 0x0075C3D8): the rows of the largest standard city. A bigger city has more rows and would use lists that do not exist (docs/city-size.md). With `[improvements] big_cities` on, ours makes as many as the size at 0x00B4BC44 when that is more than 0x100; otherwise, and always with the setting off, 0x100 as the game does. The four lines are changed by hand in the generated file, which says so at its top.

Compare mode uses the undoing: ours sets up and its result is taken; then twice the game's undoing and the game's set-up run and theirs is taken. The result is the view's globals (0x00B4C600 to 0x00B4C840), the tuning, the five arrays' contents, the number of nodes in every row layer list and the spacing of the dirty bits' pointers. A global that holds three different addresses is left out, as is anything the game's own two results disagree on.

Checked on the three tutorial cities: 1,540 dwords, no difference; the self-check is clean; the same with the big cities setting on (a standard city, so the capacity stays 0x100); ours alone with every terrain replacement runs Big City for 30 days with a volcano in the release build; screenshots after the camera workout match the game's (20 of 20). The set-up runs once a run, so this is one comparison each. The path that makes more than 0x100 lists has not run: no test has a bigger terrain yet.

### The terrain view's start and stop

The view is started for a city (0x0075C420, with the terrain) and stopped when the city closes (0x007560F0). The byte at +0x18 says it is started.

The start:

- runs the one-time set-up when it has not run (above);
- keeps the terrain (+0x20) and two more services of the city (+0x1C, +0x24), each with a reference;
- sets the size (0x007595A0, cdecl, cells across and down): when it differs from the one kept at 0x00B4C744 and 0x00B4C748, the counts derived from it are kept (vertex columns and rows, the vertex count, the index steps from 0x00B4C710 on), the drawing buffers are freed and built again ("The terrain's buffers");
- drops the textures and picks the zoom's again, and resets the kept rotation and zoom (0x00B4C708 = 4, 0x00B4C70C = 5, values no camera has, so the first frame redoes the texture coordinates);
- makes the view's parts: the overlay manager (+0x6C), the cell marks (+0x70) and four render passes (+0x78 to +0x84);
- fills the heights of every vertex, land and water (0x007569F0, 0x00756B00), sets every row's dirty bit (0x00755ED0) and redoes every cell's indices (0x00755FB0);
- forgets every cell's own texture: the counts at 0x00B4C6B8 are zeroed and each row's two vectors emptied ("A cell's own texture");
- subscribes to six messages and gives the passes to the 3D render (slot 0x80, nine calls).

The stop takes the passes back from the render (slot 0x84, eight calls), unsubscribes from the six messages, destroys the parts and releases what the start kept. The buffers and the size stay, so a next city of the same size does not build them again.

`renderer.terrain.viewinit` is the start, the stop and the three helpers (the size, the rows' dirty bits, every cell's indices), translated instruction by instruction.

**Size limits.** Nothing here has a literal size: the start takes the cells across and down from the terrain and everything follows from them. The limits are in what it calls: the row layer lists and dirty bits of the set-up (0x100 rows, above), and the buffers' 16-bit indices and counts ("The terrain's buffers").

Compare mode stops and starts the view again: ours starts it and its result is taken, ours stops it and that result is taken; then twice the game's start and the game's stop run and theirs are taken, and the game's start leaves the view started. Before each of the game's starts the kept size is forgotten, so the game frees and builds the buffers as it does for a first city. A result is the view (0x100 bytes), the globals from 0x00B4C600 to 0x00B4C840 and, when `renderer.terrain.buffers` is on, every buffer block. A dword that holds three mapped addresses, not all the same, is a pointer to something each start makes anew and is left out, as is anything the game's own two results disagree on.

Checked on the three tutorial cities: 349,215 dwords (1.4 MB) after the start and after the stop, no difference, with 176 to 256 bytes left out, nearly all of them pointers; the self-check is clean; ours alone with every terrain replacement runs Big City for 30 days with a volcano in the release build and stops the view at the end; screenshots after the camera workout match the game's (20 of 20). The start runs once a city, so this is one comparison a run. What the comparison does not see is inside the parts the start makes (they are made by the game's constructors in both runs) and the render's own list of passes.

**What is left of the terrain view.** Its code runs from 0x00751C40 to 0x0075D5B0: 146 functions, 45.8 KB. Counting what can still be reached when our replacements are on, about 45 functions are still the game's, and 30 more are only called from code that is ours already, so they no longer run (the row drawing variants at 0x007543C0 to 0x00755700 and the dynamic vertex buffer path at 0x0075C9F0 to 0x0075CB50 are among them: our passes do that work themselves). What is left: the single-cell draw (0x00752870), a command parser (0x0075A770), the debug draw (0x00759A80), and many small getters and setters. They come next, a part at a time.

## The overlays

What lies flat on the terrain (zone colours, tool highlights, decals and their shadows) is drawn by the overlay manager (the patch census's name; code 0x00735260 to 0x0073CF40, 104 functions, about 31 KB; its draw is 0x00738A50, which sets up texture matrices and calls the decal pass 0x00736790 and two more, 0x00736BF0 and 0x00737870). It has no geometry of its own: each overlay sets its state and texture and has a rectangle of cells of the terrain drawn again.

**The rectangle draw** (0x00735720: render context and four cell coordinates, inclusive) goes to one of six terrain view functions by three of the manager's fields:

| +0x16 | +0x94 | +0x15 clear | +0x15 set |
|---|---|---|---|
| clear | dynamic buffers | 0x007545C0: land vertices, the land's rows (view +0x98, +0x9C) | 0x00754910: land vertices, the water's rows (+0xC8, +0xCC) |
| clear | none | 0x007541C0 | 0x007543C0 (+0xBC, +0xC0) |
| set | either | 0x00755560: water vertices, the land's rows with water (+0xA4, +0xA8) | 0x00755700: water vertices, the water's rows with water (+0xD4, +0xD8) |

Each pair differs only in the row range and the per-row tables it reads. The land-vertex ones are the grid's row draws (strips, then the rows' extra quads); the water-vertex ones draw strips with vertex arrays only.

`renderer.overlays.rect` replaces the rectangle draw and with it all six. Compared draw by draw in the same frame, as the land pass. 2026-10-10, three test cities with the camera workout: 0 divergences (32,729, 175,779 and 66,945 rectangles; 176,977 on Big City with vertex arrays; all six functions reached); 20 of 20 screenshots with ours on.

**The decal pass** (0x00736790: the inverse of the view matrix, the render context, a vector of overlay indices) draws the overlays whose flags (+4) have 0x11, or 0x91 when the plain-water preference is set. An overlay is a 0xB4-byte record in the manager's vector at +0x98: -1 at +0 when in use, the index of its render state at +8 (the manager's +0x24, 8 bytes each), its rectangle of cells at +0xC, a matrix at +0x1C, an alpha at +0x9C (the driver's `AlphaMultiplier`), a colour at +0xA0 (set one of two ways by flag 0x40, with `EnableVertexColors` on for the first), and a texture at +0xAC or an object that gives one at +0xB0. The texture wraps by flags 0x20 and 2. The texture matrix is the overlay's matrix times the inverse view matrix, so the texture coordinates come from the camera-space position; then the rectangle is drawn with a depth offset of 2. The manager counts the decals drawn at +0xD8.

`renderer.overlays.decals` replaces it (the matrix product translated instruction by instruction, [overlay_decal_matrix.inc](../src/core/overlay_decal_matrix.inc)). The first comparison differed on Big City and Rush Hour, and so did the game against itself: the render context keeps its texture stage cache in a vector of its own (+0xE0, 0x68 bytes per stage), which the comparison did not put back between the two runs, so the second run skipped a filter change the first had made. With that vector saved and restored (for every pass that is compared this way): 2026-10-10, three test cities with the camera workout, 0 divergences (1,584, 33,511 and 33,389 passes; 29,388 on Big City with vertex arrays); the earlier terrain passes and the rectangle draws again 0 divergences with the wider comparison; 20 of 20 screenshots with ours on.

**The shadow passes** draw the overlays with flags 9 after the decals, with a depth offset of 3 and the manager's render state 4 (+0x24, +0x20): 0x00736BF0 when the manager's +0x18 is at least 3 and the preference at +0x17C (a second texture stage) is set, else the plain one, 0x00737870. Both first ask the object at 0x00B43DD0 (slot 0x24, then that object's slot 0x38) for a vector and two amounts and pass them to the context (0x007D30B0; with a positive amount also 0x007D3E90 and 0x007D2F50 with their product).

The plain pass binds the manager's shadow texture (+0xD4) once, clamped and linear, and gives each overlay a texture matrix from its second matrix (+0x5C) times the inverse view matrix. It counts at +0xDC. `renderer.overlays.shadows_plain` replaces it ([overlay_shadow_matrix.inc](../src/core/overlay_shadow_matrix.inc)). The test cities never take this path with our driver, which reports two stages, so `OPENSC4_TEST_SINGLE_STAGE=1` clears the preference each frame. 2026-10-10 with that switch, three test cities with the camera workout: 0 divergences (1,570, 32,365 and 28,908 passes; the game against itself also 0); 20 of 20 screenshots, ours against the game's pass in the same mode.

The two-stage pass (0x00736BF0) is the one normal play uses. Stage 1 gets the manager's shadow texture (+0xD4) once; each overlay then binds its own texture (+0xAC) in stage 0, with a texture matrix from its first matrix (+0x1C) for stage 0 and from its second (+0x5C) for stage 1. When the byte at 0x00B0D4CC is set, the light is scaled per overlay: the lighting object's slot 0x3C is asked at the overlay's centre (unless the manager draws water vertices, +0x16), the light vector's fourth value becomes the strength times that, an overlay whose result is below a threshold (0x00AB39A0) is skipped, and the context gets the vector again. With water vertices the rectangle goes through 0x007356D0 instead of the rectangle draw when the terrain (the manager's +0x88, slot 0xD4) counts fewer cells in it than its area. When the manager's +0x1C is 4 the shadow texture is used alone in stage 0, with the second matrix.

`renderer.overlays.shadows` replaces it ([overlay_shadow2_a.inc](../src/core/overlay_shadow2_a.inc), `_b`, `_c`: the three matrix products). 2026-10-10, three test cities with the camera workout: 0 divergences (1,584, 27,284 and 29,977 passes, with land and with water vertices, the per-overlay light on; the game against itself also 0); 20 of 20 screenshots against the stock driver. Not reached in the test cities: the single-texture case (+0x1C = 4).

**The draw itself** (0x00738A50, reached through the interface at the manager's +4): nothing when the water's rows are asked for (+0x15) with the plain-water preference; else it inverts the view matrix (by cofactors, as the grid pass does), fills the list of overlays (a static vector at 0x00B4B3B4: those in view through 0x00738390 when +0x20 is set and +0x15 is clear, else every overlay in use), takes the driver's dynamic buffers (+0x94), runs the decal pass when the preference at +0x15C is set and a shadow pass when +0x13C is, then clears the texture matrix, puts the depth offset back and gives the buffers back.

`renderer.overlays.draw` replaces it ([overlay_view_inverse.inc](../src/core/overlay_view_inverse.inc); the translator for it works from objdump's listing and reproduces the grid pass's verified matrix code exactly from the same bytes). Compare mode runs the passes as the game's in both runs and also compares the two lists. 2026-10-10, three test cities with the camera workout: 0 divergences (35,106, 30,622 and 36,250 draws; 31,062 on Big City with a single stage; the game against itself also 0); 20 of 20 screenshots against the stock driver.

**The overlays in view** (0x00738390): the manager keeps its overlays in a grid of buckets (cells shifted right by +0xE4 a side, +0xE8 buckets a row, the buckets at +0xF0 as lists of overlay indices). The terrain view gives the rows in view with their first and end columns (0x00752820); every bucket those touch is walked, and each overlay is listed once by a stamp (the manager's +0xE0, 16 bits, raised per call; the overlay's +0xA). `renderer.overlays.visible` replaces it; compare mode builds ours, then the game's, and compares the lists. 2026-10-10, three test cities with the camera workout: 0 divergences (2,476, 4,172 and 1,324 lists); 20 of 20 screenshots.

**The partial rectangle draw** (0x007356D0, through the terrain view's 0x00754C60, or 0x00754F10 for the water's rows) draws a rectangle cell by cell: each cell a quad copied from the land's vertices and raised to the water level where that is higher, split along the diagonal the terrain gives for the cell (its slot 0x118; two index lists at 0x00B4C6DC and 0x00B4C6E8). The shadow pass uses it with water vertices for an overlay partly under water. `renderer.overlays.rect_partial` replaces it. No overlay in the test cities is partly under water, so `OPENSC4_TEST_OVERLAY_PARTIAL=1` also draws every water-vertex rectangle this way, ours compared with the game's (the extra quads show, so that run is no screenshot reference). The driver keeps the pointer to the quad, which is on each function's own stack, so this comparison leaves that pointer out. 2026-10-10 with the switch: 0 divergences (2,950, 65,628 and 3,683 rectangles). Still the game's: the manager's bookkeeping (adding, moving and removing overlays).

## Models and lots

**How the 3D render draws a frame** (`cSC43DRender::Draw`, 0x007CB530; the class is 158 functions, about 40 KB, 0x007C2000 to 0x007CC000, vtable 0x00ABAB60): a pending scroll first (0x007CABE0), then the dirty rectangles (0x007C9600), the context's frame start (0x007D5230), the camera view's update (0x007F9F50 on the object at +0x114), the background (`ClearViewport`, slot 0xBC, 0x007C3F80, which despite its name restores or redraws what lies under the objects), then the passes: the static pass (0x007C7370, when the preference at +0x5C is set), a save of the picture (0x007C2960), the moving-objects pass (0x007C7830, preference +0x3C) and a last one (0x007C86D0, preference +0x2DC). The things drawn are drawables with a virtual draw (slot 0x30, given the render context), kept in a grid (+0x120) by position.

**The static pass** (0x007C7370) takes the bounds of the view on the ground (0x007C1FD0) and the cells of the grid they cover (0x005F29C0), and from each cell the items with flag 8 (+6), each once: in its own first cell, or in the first cell of the range. Each gets a key: its depth against a plane from the camera view (0x007C2F80, 0x007C2EB0, from the item's bounding box) plus the drawable's own order (its slot 0x44) in the high half. The {drawable, key} pairs are sorted (0x007C56D0) and drawn in rounds: a drawable that answers 2 is drawn again in the next round, the pairs going back and forth between two vectors (+0x134, +0x140), up to 12 rounds, with the round number in the context (+4).

`renderer.models.static` replaces the pass (the helpers above and the drawables' own drawing still the game's). Compared draw by draw in the same frame. The first comparison had the right number of draws everywhere but about one frame per view with a draw that differed, and the game's pass against itself did the same: drawables change on their first draw (a texture arrives and a placeholder goes, the tree pop-in of the first seconds). The comparison for this pass therefore runs the game's once quietly first, so both compared runs see the drawables settled. 2026-10-10 with that, three test cities with the camera workout: 0 divergences (1,242, 1,439 and 663 passes; the game against itself also 0); 20 of 20 screenshots against the stock driver.

**The moving-objects pass** (0x007C7830) walks the same cells but only those whose flag word (+0xC, bit 0) says they hold what it wants: items without flag 8, or with flag 0x80. It rewrites each cell's flag as it goes, so a cell stays flagged only while it holds such an item. Items without flag 8 go to one of three lists by their flags (1: +0x14C; 0x100: +0x140; neither: +0x134, with the drawable's order in the key as in the static pass); items with flag 0x80 also go to a fourth (+0x128). The three lists are sorted (the first by 0x007C56D0, the others by 0x007C5710) and drawn in rounds, each list compacted in place to the drawables that answered 2; the round number runs on across the lists and ends the pass at 12. The fourth list is drawn last, each with a second argument of 1 and a depth offset of 4.

`renderer.models.moving` replaces it, compared as the static pass (a quiet run of the game's first). 2026-10-10, three test cities with the camera workout: 0 divergences (47,927, 39,306 and 56,602 passes; 35,284 on Big City with cars, clouds and water effects on; the game against itself also 0); 20 of 20 screenshots against the stock driver.

**The billboard** (0x007FEA90; `this` is the object + 0x170) draws nothing for the overlaid round or below zoom 2. It keeps the zoom and rotation its picture was picked for (+0x88, +0x89); when they change (or +0x9C is set) it picks again from a heading (the x87 arctangent of its direction's +0x5C over +0x44) and a pitch (the arcsine of +0x50) through 0x007FE390, and after a change through 0x007FE400. **The model draw** (the render context's 0x007D5710: an instance, a model, properties, the overlaid flag; the two model drawables' slot 0x30 goes straight to it, 0x00801750). Properties are a flags byte (4: plain colour; 8: not in the overlaid round) and a colour at +4. With the preference at +0x3DC set, a model whose bounding box (the instance's slot 0x20) measures less on screen than a threshold is left out. The instance fills a transform (its slot 0x24: a 3x3 rotation, a position and a scale), which the context takes (0x007D3400); the colour is set through the lighting (0x007D31E0) or, for plain colour or the overlaid round, as the driver's colour multiplier. Then each of the model's groups (count from its slot 0xC): the material (slot 0x18) is set up (0x007D5310, or 0x007D5670 overlaid) and the mesh (slot 0x10) drawn (0x007D4A80); without a second texture stage a material of kind 2 (+0xB) gets a second pass (0x007D47E0). Last the colour multiplier is put back and the alpha multiplier set to 1. A debug preference (+0x35C) draws bounding boxes instead; that path stays the game's.

`renderer.models.model` replaces it (material setup and mesh drawing still the game's). **The mesh draw** (the context's 0x007D4A80). A mesh is three pointers: a vertex buffer (the format, at +6 a count that must not be 0, at +8 the vertices), an index buffer or null, and its primitive groups (a vector at +4 of {primitive, first, count}). The vertices go to the driver once (`InterleavedArrays`), then each group is a `DrawElements` with 16-bit indices from the index buffer at `first`, or a `DrawArrays` when there is none. `renderer.models.mesh` replaces it. 2026-10-10, three test cities with the camera workout: 0 divergences (592,600, 902,582 and 366,084 meshes); 20 of 20 screenshots.

**The material setup** (the context's 0x007D5310: a material and the properties). A material has 16 flag bits at +4, state values at +6 to +0xA, an alpha (0 to 255) at +8, the number of texture stages (0 to 2) at +0xB, then 0x14 bytes per stage from +0x10: the texture (by two pointers), wrap (+4, +5), filters (+6, +7), the texture coordinate source (+8), the environment mode (+9), a flag for a moving texture (+0xA) and its period (+0xC). The setup packs a render state from them (0x007D2B50, fourteen values) and applies it (0x007D4530); the properties' flags bend it: 8 dims the colour by the value at +0x10 (the driver's colour multiplier), 2 makes the model translucent by that value (blend values 4 and 5, the alpha scaled, the driver's alpha multiplier), 0x10 and 0x20 pick other values for three of the fields. Then, when the material's flag 0x20 is set, each stage: the texture and environment mode straight to the driver past the context's stage cache (the second stage only with the second-stage preference), wrap, filters and coordinate source through the context, and for a moving texture a texture matrix that scales by 1 / period and shifts by the context's two values at +0x19C and +0x1A0. `renderer.models.material` replaces it; compare mode compares the driver's state and the context after ours and after the game's. 2026-10-10: 0 divergences (1,004,240, 1,031,155 and 651,468 materials); 20 of 20 screenshots with all 21 renderer replacements on.

The overlaid round's material setup (0x007D5670: one stage, straight to the driver) is written as `renderer.models.material_overlaid` but no model in the test cities is drawn in that round, so it is unverified.

**The ground quad** (0x005E0200 after the adjustor 0x005E0540; `this` is the object + 0xEC) draws nothing in the overlaid round. It follows the context's zoom (0x005DFD40 when it differs from +0x45) and rotation (its own slot 0x10, then +0x46). It has three ways to draw: tinted when its tint mode (+0x40) is not 0xFF, translucent when a flag (+0x44) is set or its alpha (+0x3F) is below 255, else plain; the first two answer 2 in the first round, so they are drawn in the second, after everything opaque. Each way has a fixed render state (0x00B23090, 0x00B23098, 0x00B230A0) with the quad's texture (+0x48 by the index at +0x41). Tinted, the colour (+0x3C, scaled by a light value from the context's +0x44 object and by 1/255) and alpha go to the context as its light vector, with the tint mode; a preference (+0x3BC) turns mode 3 into mode 1 at half the alpha. ## Cell marks

**Data views** were the next layer in the plan, but a survey found little drawing in them: the data map is painted by the map window's own code (`cSC4WinMapView`, 0x007A0D50 to 0x007A8700, with its picture drawn by 0x007A2F60), which is interface code, and no call was found from that window into the 3D render or the terrain. What the city view does have is a pass that marks terrain cells.

**The cell marks** (class unnamed, vtable 0x00AB42F8, code 0x007504F0 to 0x00751C40; a view object of the 3D render's pass 5; its draw is 0x007514F0) are two hash tables keyed by cell (z times the width at +0xC0, plus x). The coloured ones (+0xB0, drawn by 0x00750FC0) map a cell to a colour index: each is drawn as a quad at the cell's four terrain corners, split along the terrain's diagonal, in one of a few fixed colours with an alpha per colour, with the render state at 0x00B4BDA0. In a test the first two indices came out blue and yellow and the higher ones black, which suggests the zone colours of the zoning tools; that reading is a guess from the picture. The textured ones (+0x9C, drawn by 0x00750CF0) carry a 36-byte record with a texture and are drawn with a second pair of render states. Both are drawn with a depth offset of 4. Cells are marked through the terrain view's interface (slot 0xC, 0x0075A230, which calls 0x007516D0 with a list of cells and a colour index).

`renderer.terrain.cellmarks` replaces the draw and both passes, as translations ([cell_marks_coloured.inc](../src/core/cell_marks_coloured.inc), [cell_marks_textured.inc](../src/core/cell_marks_textured.inc)). The textured marks are translated but nothing in the tests fills their table, so they are unverified.

## The data map

The Data Views window (class `cSC4WinMapView`, ID 0x28C5A41F; code 0x007A0D50 to 0x007A8700) shows a small picture of the city for the map picked in its list. The picture is not drawn through the driver: the window builds it on the CPU in a `cIGZBuffer` (class 0xC470D325, 32 bits per pixel) the size of its picture control (child 0x4203, 256 by 256 in the tests) and hands the buffer to the control, which keeps it at +0x1C. The corner minimap is something else.

- **Set map** (0x007A49B0, `SetMap(map)`): 0 for none, else the data view 0x4A0B6800 + map (kept at +0x9CC). It sets up the city view's occupant filter for the map and paints. It refuses while +0x142 is 0, which it is until the window has been shown.
- **The picture** (0x007A2F60, 6.4 KB): finds the control, makes the buffer, clears it, then switches on the map type at +0x144 (not the list's number: map 3 gives type 4, map 5 type 6). Each case asks a simulator for its map and gives it to a painter. Afterwards it walks the list of the map's icons and blits them, hands the buffer over and stamps the time at +0x9DC. A counter at 0x00B4E1A8 steps from 0 to 15, one step per picture, for the maps that move.
- **The painters** (0x007A2080 to 0x007A2F5D): a simulator's map comes as a vector of rows. The row painter (0x007A2380) takes byte rows, resamples them to the city's size when +0x94C is set (calling itself with the result), smooths them when +0x94D is set, and paints through the window's colour table at +0x54C. Three more turn rows of unsigned 16-bit, signed 16-bit and float cells into byte rows and call it; a twin (0x007A2740) does the first map type with loops of its own; and 0x007A2080 fills a 16-bit grid at +0x9B8 from two of a simulator's maps.
- **Repaints**: the window's message handler (0x007A54D0, `this` is the window + 4) repaints on message 0x86AD10EE when the picture is marked changed (+0x9D5) and the last one is 1000 ms old (250 ms for map type 0x4C).

`renderer.datamap.picture` is the picture function and `renderer.datamap.painters` the six painters, both translated instruction by instruction with `tools/re/x86cpp.py`. Their calls (222 in the picture function alone, most of them virtual) go through one helper, `DynCall`: it runs the callee on a copy of the top of the emulated stack with the emulated registers loaded, and reads back the registers, how much the callee took off the stack and whether it left a float on the x87 stack. So nothing has to be known about a callee, and register arguments (the C runtime's 64-bit shift) work without a special case.

`renderer.datamap.pixels` is the nine routines under the painters, translated the same way: for each of the two row painters a resampler to the city's size (0x0079EB40, 0x0079EFD0), the pixel loop that gives every buffer pixel its cell's colour from the table (0x0079ED90, 0x0079F230), a smoother (0x0079FEF0, 0x007A00B0) and a collector of the map's outlines for the city view (0x007A1020, 0x007A1120), plus the resize of a vector of rows (0x007A1310). They are plain functions that the game's optimiser may hand arguments in registers, so their hooks save every register, give the translation the registers and the stack as the caller left them, and put EAX, ECX and EDX back as the translation leaves them. With the three replacements on, no code of the game's own is left between the simulators' maps and the finished picture except the buffer class and the containers.

`renderer.datamap.helpers` is seven more routines the picture function uses: a blended pixel, fill and ring (0x0079DC00, 0x0079E0C0, 0x0079E130), the blit of an icon into the picture, centred, clipped and turned (0x0079E600), the marking of every cell a simulator picks with one picture (0x0079F4D0), and two small coordinate setters used through pointers (0x0079DDE0, 0x0079DDF0).

Compare mode paints ours, copies the picture out of the control, puts back what a run changes that the next one reads (the flag bytes at +0x141, +0x94C and +0x9D9 and the animation step), paints the game's with the game's painters, and compares the two pictures pixel by pixel. `OPENSC4_TERRAIN_SELFCHECK=1` paints the game's twice the same way.

Checked on the three tutorial cities with every map number from 1 to 87: 44 of them are maps (the rest `SetMap` refuses), giving 33 map types (1, 2, 4, 6 to 11, 20 to 30, 64 to 76), and every picture is the game's pixel for pixel, 132 pictures in all with no difference; the self-check is clean too, and screenshots with both replacements on match the game's. The same 132 pictures have no difference with the pixel routines ours as well. Five of the six painters ran; the grid filler (0x007A2080) did not, and neither did the map types the list's numbers do not give. Six of the nine pixel routines ran; the second row painter always took its resampling path in the tests, so its own pixel loop, smoother and outline collector (0x0079F230, 0x007A00B0, 0x007A1120) did not. Those paths are written but unverified. The outline collector's lists go to the city view, not into the picture, so the pixel comparison does not see them; only the screenshots do. With the helpers ours as well the same 132 pictures have no difference; five of the seven helpers ran, the two coordinate setters did not.

To see it in a test: `OPENSC4_TEST_DATA_MAP=<n>[,<n>...]` with `diagnostics.datamap_select=ours` (not together with `ui.map.part4`, which replaces the same message handler; the two functions are `SC4UI::F7A49B0` and `SC4UI::F7A54D0` in the address database). Before the first shot the autotest sends the advisors' script command for the window (`{0x6A5BDFCD, 0}` on the queue of the object at 0x00B43DC4), which opens it; that command's number does not pick a map, so from the second shot on the pick goes to `SetMap` from inside the window's own message handler.

To reach the two coordinate setters in a test: `OPENSC4_TEST_DATA_MAP_GRID=<day>` (token `dmgrid`, [datamap_autotest.cpp](../src/core/datamap_autotest.cpp)). They are handed to two grid mappers (0x0068C270, 0x006B4710) by the grid filler, which the picture function calls only for the map types 0x40 to 0x4B with the style 5 at +0x148, a style no data view of the game has. The test picks three such maps through `SetMap`, sets the style to 5 for one more call of the picture function each and puts it back, and hooks the two mappers for those calls to count the setters' calls and take the cells they set. 2026-10-11 on Big City, 7 days: 49,152 calls of each setter (three grids of 128 by 128 cells) with the same cells from the game alone and with `renderer.datamap.picture` and `renderer.datamap.helpers` ours; with the picture in compare mode the three pictures (map types 64, 65 and 66) have no difference. The grid filler itself was the game's in these runs (`renderer.datamap.painters` was off). Choosing maps changes what the city view shows, so from its day on the occupant parts of the fingerprint differ from a run without the test, in the game alone as well.

## The mini map

The small map in the corner is a window of class `cSC4WinMiniMap` (ID 0xCA318388, 0x96C bytes; the layout is in `src/core/ui_map_6.cpp`). The same class is the Data Views window's picture control, so there are two of them once that window is open. Like the data map it is a picture built on the CPU: the object keeps its own square of pixels (+0x114, side +0xE4) and a `cIGZBuffer` (+0xF0), and an owner can hand it a second buffer (+0xF4; this is how the data map's picture gets under it).

- **Update** (0x007A8640, slot 9 of the interface at +0xD8; called when a city is loaded and once a second): does nothing while the window or a parent is hidden or +0xFE is clear. Otherwise it redoes the terrain if +0xFD is set, marks every cell that has something on it (two bits a cell at +0x960: asked, and occupied; the occupant manager is asked once a cell), and puts the picture's pixels into the buffer (0x007A66F0), or over the owner's buffer (0x007A67F0).
- **Terrain** (0x007A7FF0): redoes the 16 by 16 cell tiles marked at +0x120, taking colours from the two tables of 256 at +0x160 and +0x560 and the sixteen at +0x108, and writes rows with one of five routines picked by the picture's scale at +0x104 (0x007A6A70, 0x007A6AD0, 0x007A6BD0, 0x007A6EE0, 0x007A6E60).
- **Paint** (0x007A79B0, window slot 88): draws the buffer into the window, works out four points through the camera (0x00800340) for the part of the city in view, and toggles the blink byte at +0x102.

`renderer.minimap.draw` is those three and the nine pixel routines under them (0x007A65D0 to 0x007A707D), translated instruction by instruction and entered with every register saved, like the data map's routines. Compare mode runs every update twice: ours, then everything it touched put back (the object, its pixels, the cell bits and both buffers' pixels), then the game's with the game's own routines under it, and the two results are compared byte for byte. An update that moves the pixels or the cells (the first, which makes them) cannot be repeated and is counted apart.

Checked on the three tutorial cities, with and without the Data Views window open: 135 updates that had work to do (the rest find the picture up to date), no difference; the self-check is clean; screenshots match the game's (20 of 20 plain, 8 of 8 with the window open). The paint is compared the same way since the small windows' work (below): a window's paint draws into the window's canvas, a `cIGZBuffer` at +0x68, so the canvas is one more thing to put back and compare. A paint that makes the map's pixels cannot be repeated and is counted apart. Eight of the twelve functions ran: three of the five row routines (0x007A6A70, 0x007A6BD0, 0x007A6EE0, for other picture scales) and the paint's pixel routine (0x007A6FB0) did not, and are written but unverified.

To reach the other scales in a test: `OPENSC4_TEST_MINI_MAP=<day>` (token `minimap`, [minimap_autotest.cpp](../src/core/minimap_autotest.cpp)) makes a mini map of its own for each of five sizes (sides 32 to 512; the tutorial cities are 128 cells wide, so the scales -2 to 2), starts it as the game does (its area, then its Init), brings it up to date twice and paints it twice on a canvas of its own. 2026-10-11 on Big City, 7 days, with `renderer.minimap.draw=compare`: the 10 updates of the test redid 640 tiles, all five row routines ran, and neither they nor the test's 5 repeatable paints differ from the game's (the first paint on a new canvas cannot be repeated); the token is the same from the game alone and with the replacement on. The paint's pixel routine (0x007A6FB0) is only used for a canvas of format 7, sixteen bits with four of alpha, which a window gets only in a 16-bit full-screen video mode: it ran once in such a run, with no difference found, but the comparison does not read a canvas of that kind, so its output is not compared. Windowed runs always get a 32-bit canvas (format 9).

## Small windows

A window's paint (window slot 88) does not go to the driver either: it draws into the window's canvas, a `cIGZBuffer` the window keeps at +0x68, which the window manager puts on screen later. So a paint can be checked like the map pictures, in the same run: ours, then the object and the pixels of its buffers put back, then the game's, and the two results compared byte for byte (`PaintCompared` in `terrain_draw.cpp`).

The interface code left fourteen such functions as drawing (docs/ui.md). All are translated instruction by instruction and are behind `renderer.windows.paints`:

- The loading screen's two draws (0x00777220, 0x007773B0; its picture object keeps buffers at +0xC, +0x10, +0x14 and +0x98) with the blend they use (0x00776C30), and the overlay picture's paint (0x00794100, which copies its picture at +0xE4 into the canvas). A plain test run reaches these.
- The paints of the progress bar (0x00797CC0), the info tip (0x00798710), the animation recorder (0x007943B0) and its frame (0x00794BF0), the pop-up menu (0x0079AA70) and its arrows (0x0079B0E0), the intro window (0x0079D490) and the picture file dialog (0x0079D6B0), and the graph control's box (0x0076B660, a line function that forwards its seven arguments to the game's line drawing). Nothing puts these windows on screen in an unattended run; `OPENSC4_TEST_WINDOW_PAINTS=<day>` with `OPENSC4_TEST_TUTORIAL_OFF=1` (`src/core/window_paint_autotest.cpp`) brings each one up and has it painted, on the screen's canvas and again on a canvas of its own, which is a picture in memory.

The advisor head view's Draw (0x004209D0) is the one that is not a window paint: it goes to the driver through the 3D render, outside a frame, so it is compared like a pass (`DrawCompared`: the head view, the render's context and camera, and what reaches the driver). It is behind `renderer.windows.paints` with the others.

A window that makes its pictures anew in a paint (the info tip builds its text and its bubble when it is stale, at +0x140 and +0x144; the arrows build a strip) cannot simply be put back: the old picture is gone. `PaintComparedRebuilt` leaves such pointers as the run made them, puts back the rest of the object and the pixels of the buffers that stayed, and compares the rebuilt pictures by their size and pixels, not their address.

Checked on the three tutorial cities, with a self-check; screenshots match the game's (20 of 20). What the comparison saw:

- The mini map's paint: 149 paints, all of which drew, no difference.
- The eight window paints the test brings up (progress bar, info tip, recorder and frame, pop-up menu and arrows, intro, picture file dialog): 32 paints a run, 96 in all, no difference; 22 of the 32 change the object or a picture (the rest are the paints on the screen's canvas, which is not a picture in memory). The intro is never started in the test, so its paint only counts down a field: only the object is compared.
- The loading screen's draw: 12 calls a run, no difference, but only one a run changes anything in the object or its buffers, so this is a thin check.
- The overlay picture's paint: thousands of calls a run, no difference, and none of them had anything to draw (the paint leaves early without a picture), so only its way out is verified.
- The advisor head's Draw: twice a run in the test (two moods, with a model), 15 driver draws, no difference on the three cities; self-check clean.
- The graph box is not compared in the same run: the picture it is given is of another buffer class (vtable 0x00AC1550), which the comparison does not read. Its check is the test's own: the graph's canvas has the same checksum with the game's code and with ours, in separate runs.

The translator learned tail calls for this (a `jmp` out of the function or through a pointer: the callee runs without our return address and its result is ours), one-operand `mul`, the sign branches and every set-on-condition.

## The city view window

The window the city is shown in (`cSC4View3DWin`) is the interface code's, but five of its functions draw and were left to the renderer (docs/ui.md):

- **Paint** (0x007F6200, window slot 88) runs once a frame. It reads its stopwatch for the time since the last paint, steps a scroll in progress (0x007CD330), stores the time in what slot 0x28 of the object at +0xE8 gives (at +0x1C) and calls that object's slot 0x54, then takes one pending item off the list at +0x140. That the object at +0xE8 is the 3D render and slot 0x54 its draw is inferred from the slot numbers, not traced.
- **The mayor rating meter** (0x007E8510) loads the meter's picture, copies its rows up to the rating's level into a new buffer, hands that to the meter's window and places and shows the arrows beside it.
- **The lighting time** (0x007E6E40) turns the clock's hours and minutes into a float, gives it to the lighting manager and asks for a full redraw (a tail call).
- **The cost indicator's amount** (0x007EAC70) and **SetScrolling** (0x007F64F0).

All five are translated instruction by instruction. `renderer.cityview.draw` has the first three, which a test run reaches; `renderer.cityview.draw_untested` has the last two, which no test reaches, so that code has never run.

The paint cannot be run twice (it is a frame, on real time), so screenshots are its check, as for the render's own pass runner. The meter and the lighting time put their results into other objects, and give the same result when run again, so they have a new kind of same-run comparison (`EffectCompared`): ours runs first and notes every object it calls into; the first 128 bytes of each object that starts with a vtable are copied, and for a picture buffer its size and a sum of its pixels; then the game's runs twice. Bytes that differ between the game's two runs (addresses of things made anew, counts) are left out; the rest must be the same after ours as after the game's.

Checked on the three tutorial cities: screenshots match the game's (20 of 20 each); with the city running for 30 days the meter is compared twice a run and the lighting time once, over 14 and 4 objects, with no difference, and the self-check is clean. That is few calls: the meter only changes with the rating, and the lighting only when the clock's time is handed over.

For this the translator learned `adc` after an `add`, and to carry the flags of a jump to its target when the code above cannot fall into it; it reports where flags of different kinds meet and are then read. No branch of the translations already in the tree changes under the new rule.

To reach the last two in a test: `OPENSC4_TEST_CITY_DRAW=<day>` (token `cvdraw`, [cityview_draw_autotest.cpp](../src/core/cityview_draw_autotest.cpp)) sets the cost indicator five times through the view's interface (slot 42), fades it and switches it off (slot 44), and starts and stops the scrolling in the same tick (slot 33, four calls). `renderer.cityview.draw_untested` has no comparison of its own, so the token is the check: the amount's picture and the indicator's fields after every call, and the scroll fields after each SetScrolling. 2026-10-11 on Big City, 7 days: the amount drawn 5 times and SetScrolling called 4 times, with the same token from the game alone (twice), with the replacement on and in its compare mode. The test changes the advisors' part of the fingerprint from its day on, in the game alone as well; which of its calls does that was not looked into.

## The region view

The region screen's code is the Region work's (docs/region.md), which left its four draw functions to the renderer. Unlike the windows above these do go to the driver, so they are compared like the terrain passes, in the same frame (`DrawCompared`).

- **The picture grid** (`SC4RegionViewGrid::Draw`, 0x007B28B0): called in the 3D view's draw pass, it copies the grid of cached map pictures to the screen.
- **The terrain overlay** (`SC4RegionOverlay::Draw`, 0x007AB630): a render state, four vertices on its stack and one draw through the render context it is given.
- **The overlay window's paint** (`SC4RegionOverlayWin::Paint`, 0x007A9D60): the marks that drift over the region. Every frame it sets the driver up and draws each mark as a textured quad, then steps the marks by the time since the last frame, makes a new one with a chance of 0.003, and frees those past the right bound.
- **The mask of a city's picture** (`SC4CityFiles::DrawPictureMask`, 0x005DCCF0).

`renderer.region.draw` has all four. The first three run while the region screen is up; the mask is drawn when a city is saved, eight times a save, so a save test (`scripts/run-save-test.sh`, in a disposable folder) is what reaches it.

The region screen is not drawn in an unattended run: the test puts it up and loads the city at once. `OPENSC4_TEST_REGION_HOLD=<ms>` (with `OPENSC4_TEST_REGION_SCREEN=1`) keeps it on screen for that long first.

The overlay window's paint does not repeat by itself, so its comparison takes three steps:

- The marks' nodes are put back with the window between the two runs, and a frame that would free a mark is not repeated (counted as unrepeatable).
- The window's stopwatch keeps the clock's reading of its last restart, and the step moves every mark by the real time since then. Both are put back for the second run but cannot be compared byte for byte, since the second run starts later. The step is checked by its shape instead: in each run every mark must have moved by its speed times one same time.
- A frame in which a mark is made ends with a new node at a different address in each run. Such a frame shows as a divergence in the list's links. They are counted on their own, and the self-check has them too.

Checked with the region screen held for 20 seconds, three runs and a self-check:

- The overlay window's paint: 50,897 frames compared. The drawing, the window and the marks are the same in all but 144 of them, and exactly 144 frames made a mark; the self-check has 54 of each in 18,029 frames. The step has the right shape in every frame. 280 frames freed a mark and were not repeated.
- The picture grid and the terrain overlay are drawn once a run (the region's 3D view only redraws when something changes): no difference in the three runs, which is a thin check.
- The mask of a city's picture: a save of each tutorial city draws it eight times, so 24 masks are compared (8,072 driver draws in the Making Money save): no difference, and the self-check is clean.

There is no screenshot harness for the region screen, so the picture on screen is not compared.

## Water effects, sky and clouds

**What draws after the models.** Besides the models, the 3D render calls objects that registered for one of four passes (`cSC43DRender::AddViewObject`, 0x007C5D90: pass 0 and 2 around the static pass, 3 and 5 around the moving-objects pass; each object's slot 0xC with the render context, in the order number's order). `diagnostics.trace.viewobjects` logs every registration; `OPENSC4_VIEWOBJECT_SKIP=<draw function>` leaves an object out, to see in a screenshot what it draws. In a loaded city (2026-10-10):

| Pass, order | Draw function | What |
|---|---|---|
| 0, 0 and 2, 1000 | 0x0075BFD0 | the terrain view: land, then water |
| 2, 0 and 1100; 5, 1000 and 1100 | 0x00739490 | four overlay managers |
| 5, 1000 | 0x0046D990 | not identified yet (5.6 KB) |
| 5, 1000 | 0x007514F0 | the terrain view again: coloured and textured cell quads from two hash tables (+0xB0, +0x9C) |
| 5, 1000 (three objects) | 0x00620500 | not identified yet: quads from two trees, drawn twice |
| 5, 1100 | 0x00761FF0 | the shore: the surf line along the water's edge |
| 5, 1900 | 0x00593120 | the effects manager: every particle effect, the clouds and their shadows among them (below) |

There is no sky in the city view: what shows behind the terrain is the background the 3D render restores (`ClearViewport`). The clouds are particle effects: an effect's description carries a render flag (the effects parser's `kRenderWaterEffects` 3 and `kRenderCloudsAndFog` 4, the numbers of the render properties of those names), and with the effects manager left out the clouds and their shadows are gone and nothing else in the paused test city changes.

**The shore** (class name ours, `STEShore`: vtables 0x00AB45FC and 0x00AB4624, code 0x0075FAE0 to 0x00762100; the 3D render holds the interface at the second vtable). Its draw (0x00761FF0) builds the strips on the first draw (0x00761B70, from the terrain's cells whose record has flag 0x10 and not flag 1 at +0x22) and sets them up for the zoom (0x00761CF0, again whenever the context's zoom differs from +0x40). Then, when the `RenderWaterEffects` property is set (the byte at +0x7C of the render properties), it applies one fixed render state (0x00B4D528, filled on first use) and draws each group (0x38 bytes each, +0x34 to +0x38) whose bounding box (+0x20, +0x2C) the camera view has in sight: for each strip in the group's list (+0xC), again by its own box (+0x34, +0x40), the texture its index (+0xC) picks from the object's table (+0xB4) and its 24-byte vertices as one strip (primitive 7, vertex format 10; 0x0075FE70).

`renderer.water.shore` replaces the draw and the strip draw (building the strips and the zoom change still the game's). Compared draw by draw in the same frame as the terrain's passes; frames that build or change zoom run the game's only, because they allocate. 2026-10-10, three test cities with the camera workout and water effects on: 0 divergences (63,600, 64,584 and 81,191 calls of the draw; the game against itself also 0); 20 of 20 screenshots with ours on against the same run without it.

**The effects manager** (class name ours, `SC4EffectsManager`; the 3D render holds the interface at the object's +4, vtable 0x00A9F250; offsets below are from the interface). Its draw (0x00593120) does nothing when the render property at +0x39C is set. Else, after a call on a helper object (0x00586720, when +0xD98 is set), it empties two vectors and walks three lists of effects (index vectors at +0xBF0, +0xC38 and +0xC5C into the tables at +0xBE4, +0xC2C and +0xC50). An effect that is running (its slot 8) and whose box (0x005B26F0) the camera view has in sight, or whose description has flag 0x10, goes into the vector of {depth, effect} at +0xDA0, the depth being its position (+0x194) along the axis the rotation looks down, signed, plus an offset from its description (+0xD8); the others go into the vector at +0xDAC. The particle budget (+0xC9C) is then steered by the particle count of the last frame (+0xC8C) against the target from the render properties. The vector is sorted by depth (the game's own sort helpers, 0x005906C0, 0x0058F980 and 0x0058E170), and with the render property at +0x1BC set each effect in it is drawn (slot 0x24 with the frame's step, +0x1B8, and the render context) and its particles (+0x18) counted, and each effect out of view gets the same call without a context, last to first. A debug property (+0x35C) draws the boxes. Then every running entry of a fourth list (+0xBC0, index vector +0xBCC) is drawn (its slot 0x24), and three more steps follow: 0x0058E870 when +0xD44 is above 0 and the property at +0x3FC is set, 0x0058EC40 when +0xD88 is above 0, and 0x005922A0 always.

What it draws in the test cities (`diagnostics.trace.effects` counts by class; Big City with clouds and water effects on): the sorted effects are of two classes (vtables 0x00AA0C58 and 0x00AA0EA0) that share one draw (0x005B8540), and the fourth list's entries are of one (vtable 0x00A9EE78, draw 0x00582920, about 250 a frame).

`renderer.effects.draw` replaces the manager's draw with a translation by [tools/re/x86cpp.py](../tools/re/x86cpp.py) ([effects_draw.inc](../src/core/effects_draw.inc)); the effects' own drawing is still the game's. The draw cannot be run twice in a frame, because effects move on when drawn (a first comparison that did so ended the game). So compare mode runs ours with the calls that draw or step something only recorded (detours on the six functions above), puts the manager back, runs the game's with the same calls recorded and made, and compares the two records and what the draw itself works out: the two vectors and their contents, the budget and the number of effects drawn. Left out: the particle count, which adds up what each effect's draw leaves behind, and the fourth list's draws, because drawing an effect adds and removes entries of that list (the game against itself differed there in 7% of frames). 2026-10-10, three test cities with the camera workout, clouds and water effects on: 0 divergences (79,562, 62,201 and 87,541 draws; the game against itself also 0). Screenshots on Big City with ours on: with clouds 16 of 20 against the same run without it, where two runs of the game without it give 17 of 20 (the clouds drift at zoom 1); with clouds off 19 and 20 of 20 against two runs without it, the one miss industrial smoke at zoom 1 (1.46% of pixels against a limit of 1.2%; those two runs match each other).

**An effect** (class name ours, `SC4Effect`; two classes, vtables 0x00AA0EA0 and 0x00AA0C58, which differ in seven slots, among them the drawing without a texture, slot 0x44, and what is done when nothing is drawn, slot 0x4C). Its draw (0x005B8540, slot 0x24, shared by both; the step and a render context, null for an effect out of view) does nothing unless the effect runs (+9). It adds the step to the effect's clock (+0x110; when +0x118 is set, once, plus the description's +0x1C), asks the object at +0x1F0 for a value (+0x1FC), and for descriptions with flags runs extra steps (0x005B7030 for 0x2000, 0x005B8410 for 0x80000000). The velocity of the frame (+0x13C) is the description's (+0xE0) plus the effect's own (+0x150) plus one along a path when the description has one (0x005B6C40, else zero) plus a vector the effect points to (+0x1E8, at its +8) times a factor of the description (+0xEC). Then every particle of the list at +0x14 (nodes of next, previous and the particle) whose first byte says it runs is stepped (the class's slot 0x50, 0x005B9BA0: its age against its life, its position by the velocity); one that has ended is unlinked, its node freed, the count (+0x18) lowered and the particle given back through the sub-object at +4 (slot 0x40). New particles are emitted (slot 0x3C, 0x005B96E0, unless +0x21A). With a render context and particles left it draws: slot 0x38, a context call for descriptions with flag 1 (0x007D31B0, undone after the drawing by 0x007D3290), the render state at +0x1C, then slot 0x48 (0x005B4B90) when +0x1EC is set, else slot 0x44; without, slot 0x4C. Last the sub-object is asked whether the effect is over (0x005B9D40), and if not, descriptions with flag 0x800000 get one more step (0x005B2730).

`renderer.effects.effect` replaces the draw with a translation ([effect_draw.inc](../src/core/effect_draw.inc)); everything it calls is still the game's. It changes the effect and frees memory, so it cannot run twice either, and what it does next depends on what its steps leave in the effect. Its compare mode therefore records and replays: the game's draw runs for real, with detours on thirteen functions it calls noting each call, what the two that steer it answered (the particle's step and the end check), and which bytes of the effect, its list nodes and the particles' first bytes the call changed; the effect is put back as it was; ours runs with no call made, each answered and its changes applied from the record; the two call lists, the results, the lists of particles and the effects are compared; and the effect is put back as the game left it. While this goes on the drawing thread's frees are held back (detours on the two free functions): another thread of the game allocates from the same allocator, and without that the memory of a freed node could be handed out and then overwritten by the comparison, which ended several test runs at random. 2026-10-11, three test cities with the camera workout, clouds and water effects on: 0 divergences (522,900, 374,157 and 344,166 draws). Screenshots on Big City with the three replacements of this section on: with clouds 16 of 20 (the clouds drift); with clouds off 20 of 20 against each of two runs without them.

**A particle's step** (0x005B9BA0, slot 0x50 of both effect classes: the particle and the step). A particle starts with a byte that says it runs, then its age (+4) and life (+8), its position (+0xC) and its velocity (+0x1C). The step adds the step's time to the age and, when the age has reached the life, clears the first byte and answers false. Else the velocity takes the effect's velocity of the frame (+0x13C) times the step and is multiplied by a constant (0x00A81228) minus the step times a value of the description (+0x100), and the position moves by the step times a constant (0x00A92D28) times the sum of the old and the new velocity. Descriptions with a flag of the mask at 0x00B22E14 are stepped by another function (0x005B9790) instead.

`renderer.effects.step` replaces it with a translation ([effect_step.inc](../src/core/effect_step.inc)); the other step is still the game's. It reads the effect and writes only the particle, so compare mode runs ours on the particle, keeps what it left, puts the particle back and runs the game's (particles of the other step are not compared). 2026-10-11, three test cities with the camera workout, clouds and water effects on: 0 divergences (7,493,036, 9,703,075 and 13,117,166 steps). ## What the driver calls mean

Reference for writing a driver, from decompiling both stock drivers (vtables: DirectX 0x00AC4660, OpenGL 0x00AC36D0, `cIGZGDriver` at object + 0xC in both). The OpenGL driver is the plainest spec, since most methods are one GL call after a table lookup; the DirectX driver is what the game was tuned against and what the screenshot harness compares with (the OpenGL driver renders without terrain and with black boxes around trees on a current NVIDIA card, so it is no visual reference).

**The model is OpenGL 1.3 fixed function with `ARB_texture_env_combine`.** GD enums are indices into translation tables (OpenGL driver 0x00B12010-0x00B12238, DirectX driver 0x00AC44CC-0x00AC45F8); [gd.h](../src/core/gd/gd.h) lists them.

- **Window.** `SetVideoMode(mode, wndproc, ?, ?)` creates the driver's own ANSI window ("GDriverClass (DirectX)": `WS_OVERLAPPEDWINDOW | WS_VISIBLE` sized to the mode's client area for windowed modes, a popup otherwise), stores the driver in `GWLP_USERDATA` and sends every message to `wndproc`. Mode -1 destroys it. `SetGDriver` calls `SetVideoMode` itself when a mode is already set. Modes are `sGDMode` records of 0x34 bytes (index, width, height, bits per pixel, A/R/G/B masks, a full-screen flag at 0x20, then capabilities the game configures itself from; see "What the game asks the driver"); the DirectX driver lists 120 here, every desktop resolution twice (full screen and windowed).
- **Frames.** `Flush` presents: `glFlush` + `SwapBuffers`, or the DirectX driver's blit to the primary surface. The back buffer keeps its contents between frames, which the game relies on: it redraws only what changed. `Clear(mask)` takes 0x4000 colour, 0x1000 depth, 0x2000 stencil and clears the current viewport (a Direct3D 7 clear), with the values from `ClearColor`/`ClearDepth`/`ClearStencil`. `ColorMask` is a no-op in the DirectX driver.
- **Viewport.** GL coordinates, origin bottom left: the DirectX driver clamps to the surface and converts with `top = height - y - h`; `GetViewport` returns `{x, y, x + w, y + h}` in the same coordinates. Direct3D 7 viewports clip, so a viewport also acts as a scissor rectangle (the OpenGL driver sets `glScissor` with it).
- **Matrices.** `MatrixMode` 0 model-view, 1 projection; GL layout. The DirectX driver loads the model-view as the world matrix (view = identity) and rewrites the projection for Direct3D (depth range and half-pixel offset, which is why it reloads it on every viewport change).
- **Vertices.** `InterleavedArrays(format, stride, data)` only records the pointer (stride 0: the format's); `DrawArrays(prim, first, count)` and `DrawElements(prim, count, type, indices)` read from it, with unsigned byte, short or int indices. Formats are bit fields of per-element counts (position, normal, up to 3 colours, 1D-4D texture coordinates), with legacy IDs for common layouts ([vertex_format.h](../src/core/gd/vertex_format.h)). **Colours are D3DCOLOR (BGRA bytes)**: the OpenGL driver swaps red and blue in the caller's array before each draw and back after. Primitives: triangles, strips, fans, points, lines, line strips, quads, quad strips; the DirectX driver turns strips, fans and quads into indexed lists.
- **Colour.** `ColorMultiplier(r, g, b)` and `AlphaMultiplier(a)` switch on lighting with only an ambient light, and leave it on. In the DirectX driver (0x00883240, 0x00883310, 0x008833E0) the lit colour is the ambient material times the multiplier, where `EnableVertexColors(diffuse, specular)` picks the ambient material (vertex colour if `diffuse`, else white); the lit alpha is the diffuse material's, which `EnableVertexColors` sets to the vertex colour if `specular` is set and to the material otherwise, `AlphaMultiplier(a < 1)` sets to the material (alpha `a`), and `AlphaMultiplier(1)` sets back to the vertex colour if the last `specular` was set. (Ghidra's decompile of 0x008833E0 shows a constant for that argument; the disassembly reads `[esp+0x10]`, the second argument.) Cloud shadows depend on it: they redraw the terrain with `ColorMultiplier(0, 0, 0.2)`, `AlphaMultiplier(0)` and an alpha test of 0.22, so with the material's alpha of 0 the stock driver draws almost nothing there. Vertices without a colour use the material.
- **Textures.** `CreateTexture(format, w, h, levels, hints)` returns a handle (formats RGB5, RGB8, RGBA4, RGB5_A1, RGBA8, DXT1 with alpha, DXT3, DXT5); `LoadTextureLevel(texture, level, x, y, w, h, format, type, rowLength, pixels)` uploads (source formats RGB, RGBA, BGR, BGRA, alpha, luminance, luminance-alpha, DXT1/1A/3/5). `SetTexture(texture, stage)`, `GetTexture(stage)`; the GL-style `GenTextures`/`BindTexture`/`TexImage2D` exist but were not called in our runs. `TexParameter` 0-3 are min filter, mag filter, wrap S, wrap T, per stage.
- **Texture stages.** `TexStage(n)` selects the stage that `Enable(Texture2D)`, `TexEnv`, `TexParameter`, `TexStageCoord`, `TexStageMatrix` and `TexStageCombine` apply to. `TexEnv(int)` sets the GL texture env mode (replace, modulate, decal, blend, combine); `TexEnv(float*)` sets the constant colour (Direct3D's texture factor). `SetCombiner(combiner, stage)` takes a 10-byte `cGDCombiner`: RGB op, three RGB args, alpha op, three alpha args, RGB and alpha scale; an arg's low nibble is the source (texture, previous, constant, primary colour), the high nibble the operand (colour, one minus colour, alpha, one minus alpha); RGB op 0xFF leaves the stage alone. `TexStageCoord(n)`: the low 3 bits pick the coordinate set, 0x10/0x20/0x30 generate coordinates from the camera-space position, normal or reflection vector.
- **State.** `Enable`/`Disable`: 0 alpha test, 1 depth test, 2 stencil test, 3 culling (clockwise faces), 4 blending, 5 texturing on the current stage, 6 fog, 7 nothing. Depth, alpha and stencil functions, stencil ops, blend factors and shade model are GL's lists in GL's order. `PolygonOffset(n)` is a depth bias: the DirectX driver (0x00883710) sets Direct3D 7's `D3DRENDERSTATE_ZBIAS` (0-16, higher draws in front) to `n`. The game calls it about once per object, always with 0 in the test city.
- **Fog.** The DirectX driver supports only vertex fog, and only when the device reports it: `Enable(6)` sets `D3DRENDERSTATE_FOGENABLE`, `Fog(mode, value)` sets `D3DRENDERSTATE_FOGVERTEXMODE` (exp, exp2, linear), `Fog(param, float*)` sets the colour, density, start and end (0x00883100, 0x00883180). Neither driver received a fog call in the test city, with `RenderCloudsAndFog` on or off: the clouds are drawn as textured sprites and terrain passes, not with fog.
- **Errors.** Methods set an error code that `GetError` returns and clears (DirectX driver: 1 bad enum, 2 bad value, 3 unsupported, 6 failed mode set).
- **Not implemented by either driver:** the six blits (`BitBlt`, `StretchBlt` and their alpha variants) only set an error. `GetBoolean` and `GetFloat` are empty in the DirectX driver; `GetInteger` answers only the unpack row length.
- **Buffer regions** (`cIGZGBufferRegionExtension`): `NewBufferRegion(surface)`, with 0 the back buffer (the render target) and 1 and 2 depth, returns a handle (from 1) to a surface-sized copy (until 2026-10-09 our driver took 0 for the front buffer and 1 for the back buffer, so the city view saved and restored the wrong pictures; nothing showed it until photo mode hid every interface window); `ReadBufferRegion(h, rx, ry, w, h, x, y)` copies (x, y, w, h) of the surface to (rx, ry) in the region, and `DrawBufferRegion(h, rx, ry, w, h, x, y)` copies (rx, ry, w, h) of the region back to (x, y) of the same surface: the region's position comes first (the DirectX driver's blits, 0x008853B0 and 0x008855F0). Top-left origin. The game uses them to restore parts of the frame instead of redrawing them (about 16,600 draws per 120 s), and to scroll the city view: it moves the saved picture and draws only the strip that comes into view. Until 2026-10-06 our driver had the two positions swapped, which made no difference while they were equal (all 20 shots matched) but scrolled the picture the wrong way, leaving streaks where the new strip should be.
- **Snapshots** (`cIGZGSnapshotExtension`): `CopyColorBuffer(x, y, w, h, buffer)` copies part of the front buffer into a 32-bit `cIGZBuffer`, creating one (class 0xC470D325) if `buffer` is null, and returns it.
- **Dynamic vertex buffers** (0x09CD86F9, a separate object; DirectX driver vtable 0x00AC4F10 over Direct3D 7 vertex buffers): slot 3 `GetBuffer(vertexFormat)` returns a handle (always 0 in the DirectX driver), 4 the buffer's format, 5 its capacity in vertices (64 KB worth: 2,048 of the 32-byte format 0xB), 6 `Lock(buffer, count)` reserves `count` vertices after the previous batch, starting over at 0 when they do not fit, starts a new batch and returns a pointer to write them to, 7 `Append(buffer, count)` extends the locked batch, 8 `Unlock`, 9 `Draw(buffer, primitive)` and 10 `DrawIndexed(buffer, primitive, count, uint16 indices)` draw the batch with the current state (indices relative to its first vertex), 11 resets every buffer. The terrain (0x007545C0) and the scene renderer (0x00593E10) draw through it, about 180,000 queries per 90 s shots run; the stock OpenGL driver does not offer it, which is one reason it draws no terrain.
- **Texture transforms.** `TexStageMatrix(m, inputs, outputs, flags)`: the terrain shadow projection uses camera-space coordinates (`TexStageCoord(0x10)`) with (4 inputs, 2 outputs, flag 1). The DirectX driver negates the matrix's third row in that case (and for 3 inputs without flag 1); in our driver the matrix as given matches the stock output better, so Direct3D 7's camera space evidently has the opposite z. The OpenGL driver instead generates only s and t from the eye position.

## D3D11 driver

`renderer.d3d11` ([src/core/gd](../src/core/gd)) is OpenSC4's own driver. The driver ([driver.cpp](../src/core/gd/driver.cpp)) keeps the game's state the way the DirectX driver does and calls a backend interface ([backend.h](../src/core/gd/backend.h)); the D3D11 backend ([d3d11_backend.cpp](../src/core/gd/d3d11_backend.cpp), shaders in [d3d11_shaders.h](../src/core/gd/d3d11_shaders.h)) is the only one so far, and a Vulkan one can sit beside it.

**It takes over the OpenGL driver's class ID (0xC4554841), like scvk and SCGL, and is selected whenever it is on** (Dan's choice for now, 2026-10-06; later a menu option): a detour on the driver choice (`cSC4App::SelectGraphicsDriver`, 0x0044CE40) requests it when no `-d:` option names a driver, then restores the saved choice the game would otherwise overwrite, so turning the driver off leaves the user's settings as they were. `-d:DirectX` still picks the stock driver. The first version was made current at PreAppInit with `SetGDriver`, like the pass-through driver, and drew the UI correctly but no terrain or model textures: the game creates 3D textures through a driver pointer it cached before PreAppInit, so they went to the stock DirectX driver and the handles it then bound on ours were unknown. Created by the graphics system at startup, the driver gets everything. It lists its video modes as the DirectX driver does (see "Resolutions"). Full-screen modes change the display mode as the OpenGL driver does (0x0087FC90: width and height only, `CDS_FULLSCREEN`, the desktop's settings back when the mode goes) and use a popup window; a mode the size of the desktop leaves the display alone, which makes it borderless full screen. Switching away from the game gives the desktop its resolution back until the game is active again. Showing a smaller mode scaled on an unchanged desktop is left for later: the game calls `GetCursorPos`/`ScreenToClient` and `SetCursorPos`/`ClientToScreen` itself, so mouse coordinates would need translating in those places too. Tested unattended: 1024x768 full screen on a 1920x1080 desktop matches the windowed run in all 20 shots, and 1920x1080 full screen renders (the game needs `-CustomResolution:enabled` for that size, with either driver; `OPENSC4_GAME_WINDOW="-f -CustomResolution:enabled -r1920x1080x32"` replaces the scripts' default `-w`).

- The back buffer is a texture of our own that keeps its contents; `Flush` copies it to a front-buffer texture, which the window shows as described under "Frame pacing". Buffer regions and snapshots work on these textures; depth regions and clears go through a small full-screen shader, because Direct3D 11 cannot copy part of a depth buffer.
- Drawing: vertices and indices go through ring buffers (the game's arrays are only valid during the call); fans, quads and quad strips become indexed lists; elements a vertex format lacks come from a stride-0 buffer of defaults. One vertex shader does the transforms, the ambient-only lighting, texture coordinate generation and texture matrices, and per-vertex fog; one pixel shader (and a flat-shaded twin) runs up to 8 texture stages of GL texture environment modes or combiners, the alpha test against the game's byte reference, and fog. Input layouts, samplers, blend, depth-stencil and rasterizer states are cached. Textures are BGRA8, or BC1-3 for DXT data that fills whole blocks; uploads are converted on the CPU ([pixels.cpp](../src/core/gd/pixels.cpp)).
- The dynamic vertex buffers keep CPU copies and draw through the same path.
- `d3d11.dll` and `d3dcompiler_47.dll` are loaded only when the driver starts; `debug_layer = on` in `opensc4.ini`'s `[renderer]` section (or `OPENSC4_RENDERER_DEBUG_LAYER=on`) turns on the debug layer. The log records the first occurrence of each primitive, vertex format, texture format, upload format, sampler and stage setup (up to 64 of each).

Texture stages follow the DirectX driver's Direct3D setup (0x00884320, 0x00884500) rather than GL's: the first stage that is off, lacks a texture or uses the blend env mode (which that driver does not implement) ends the cascade; filters map as it maps them, including its `LinearMipmapNearest`, which a missing `break` turns into point-filtered with linear mipmaps; textures created as RGB5 or RGB8 sample an alpha of 1 whatever the uploads hold; modulate on a texture without alpha keeps the current alpha.

**Status: renders the city like the stock driver.** Against the stock DirectX driver in the screenshot harness (2026-10-06, Making Money Tutorial), all 20 shots pass `--tolerance 32 --max-differing 1.2`, at most 0.6% of pixels off by more than 32, all of them deer, which move in real time. With `RenderCloudsAndFog=1` (which the harness turns off because clouds drift in real time), 18 of 20 pass and the two others (zoom 1) differ where the clouds have moved; before the diffuse-source fix above, our driver drew cloud shadows as opaque dark-blue blobs. The tree shadows long had a dark halo that no rendering change fixed: the game drew them differently for our driver, because the driver reported weaker capabilities than the stock one (see "What the game asks the driver" below). `PolygonOffset` maps a z-bias of `n` to a depth bias of `-n` units plus a slope-scaled bias of `-n`, as Wine's OpenGL backend maps `ZBIAS` (`glPolygonOffset(-n, -n)`); unverified, because the test city never sets one. Fog follows Direct3D 7 vertex fog (camera-space depth) and is logged on first use; also unverified, for the same reason. Not done yet: `TexImage2D` (not called). Menus, the region view and UI interaction have not been tried on it yet ([run-game.sh](../scripts/run-game.sh) plays the game in the test user folder).

### Resolutions

The game picks a mode from its video preferences (saved in `SimCity 4.cfg`) or `-r<width>x<height>x<depth>`, `-w` and `-f`; with the command line, sizes outside its own list need `-CustomResolution:enabled` (with either driver, or it quits at startup), which is how players get widescreen sizes.

**Mode list.** The DirectX driver lists the desktop's resolution first, then every other resolution the display offers, each as a full-screen and a windowed mode, all at 32 bits and then all again at 16 bits (144 modes on the AW3423DW; seen with `diagnostics.d3d7_probe`). The D3D11 driver lists them the same way (96 here), so the game picks the same mode indices (11 for 1024x768 windowed, 58 for 1024x768 16-bit full screen). It must: when no mode matches the preferences the game crashes before setting one (0x0098E9A6, an object at + 0xE4 missing). The first version listed only 32-bit modes and, like the OpenGL driver, windowed modes smaller than the desktop, and crashed with a saved 16-bit full-screen preference, which the graphics rules recommend on cards they do not recognise. The driver renders in 32 bits whatever the mode says; in full screen it changes only the display's size (Windows offers no 16-bit desktop modes).

**Settings.** `opensc4.ini` `[renderer]` `resolution` (`WxH` or `desktop`) and `window` (`windowed`, `fullscreen` or `borderless`) override the game's video preferences in memory just before it picks its driver and mode (in the `cSC4App::SelectGraphicsDriver` detour), as sc4-graphics-options does to the saved preferences; colour depth becomes 32 bits. `borderless` is full screen at the desktop's size, which needs no display mode change. No `-CustomResolution` is needed this way, and the game does not write the overridden values to `SimCity 4.cfg` (checked: the next start sees its own preferences again). Unset, the game's own options apply.

**The >2048 px crash is in the stock DirectX driver, not the game.** At 3440x1440 full screen (desktop size, 2026-10-06, Alienware AW3423DW) the stock driver crashes at 0x00884FE1 in its `Disable`: the per-stage state array at driver + 0x11C is null, so its device setup failed silently and the first state change writes through a null pointer. The D3D11 driver runs the same city at 3440x1440 with no problem (20 screenshots and a full test run), so with it the cap is gone.

A windowed size larger than the desktop crashes in game code instead (0x0098E9A6, an object at + 0xE4 missing; tried 2000x1000 and 2560x1440 on a 1920x1080 desktop), which matters only for testing: the window cannot be bigger than the screen anyway.

### Frame pacing

`Flush` is not a frame boundary. The framework's main loop (0x008795BD) never waits while the game runs: it handles window messages, then calls the framework's idle step (0x0087A812), which ticks every tick service (the simulation among them) and every fourth pass the on-idle services, among them the window manager's update (0x0098E5C0), which draws the software cursor and calls `Flush` when the view changed. How often that happens depends on what the loop is doing (2026-10-06, D3D11 driver, logged every 10 s):

| Phase | Flushes per second | Frames shown per second (175 Hz display) |
|---|---|---|
| Start-up and loading screens | about 20,000 | 172-174 |
| City running at speed 2 | about 15 | about 20-30 (front-buffer updates count too) |

So while the simulation runs, the game itself redraws the city about 15 times a second; the stock driver's total flush count over the same run is similar. Changing the on-idle interval (`cIGZFrameWork::SetOnIdleInterval`, default 4) to 1 or 16 made no difference to either rate or to the simulation.

Waiting for vertical sync in `Flush` starves that loop: in a 60 s run at speed 2, a blocking `Present(1)` showed 7.5 frames per second and the city reached 2010-01-25, where the stock driver reached 2011-12-09. So the driver paces what the window shows, not the game: a flip-model swap chain with a frame-latency waitable object (maximum latency 1). `Flush` copies the back buffer to the front buffer and posts the driver's window a message; the front buffer is presented when the game's main loop dispatches it, between passes, if the waitable object is signalled (else a 10 ms window timer retries). **Presenting inside `Flush` showed stale pictures** (seen by Dan on 2026-10-06, the first time anyone watched the driver live): some flushes come in the middle of a redraw, after the 3D view's saved image is restored and before the changes are drawn, and the first version presented the first `Flush` after the display was ready, which kept such an image on screen for a whole refresh. Grabbing the screen 40 times in a row (20 ms apart) on a static view showed earlier images coming back (`E F E G ... E`); with presentation between loop passes none do. The stock drivers show every `Flush` at once, so the intermediate images last only microseconds there. The CPU is kept at most 3 flushes ahead of the GPU with event queries, since nothing else blocks (the GPU is not the limit: about 20 us of waiting per flush). Same 60 s run: the city reaches 2011-12-16, as with the stock driver. `vsync = off` in `opensc4.ini`'s `[renderer]` section (or `OPENSC4_RENDERER_VSYNC=off`) presents every `Flush` at once (tearing allowed where supported); without flip-model support (before Windows 8.1) the driver falls back to a blt-model swap chain presenting every `Flush`.

**The game caps its frame rate by simulation speed** (what sc4-disable-fps-limits patches): `cSC4Simulator`'s speed setter (0x00702430, from `SetSimSpeed` and `Init`) stores 30, 20 or 15 frames per second for turtle, rhino and cheetah in the simulator at + 0x84 (the interface pointer's offset; a cheat, message 0x0AC07E24, also sets it). The only reader (0x00703EDD, found with a hardware read watchpoint; 0x00703E70 reads it as + 0x7C from a base 8 bytes further on) turns it into the simulation's time slice per frame: 1000 / cap ms, or 1000 / 30 under a condition at + 0x28 / + 0x2C, minus the time a timer at + 0x58 measured, at least 15 ms, stored at + 0x70. So the cap splits each loop between simulating and drawing. Measured in the test city at cheetah for 60 s (D3D11 driver, the field set after `SetSimSpeed`):

| Cap | Redraws per second | Simulation reached |
|---|---|---|
| 15 (the game's) | 15 | 2011-12-08 |
| 30 | 29 | 2011-12-01 |
| 60 | 57 | 2011-11-29 |
| 255 (sc4-disable-fps-limits) | 57 | 2011-12-02 |

Above about 57 the 15 ms minimum slice is the limit. In this small city the simulation does not use its whole slice, so four times the redraws cost almost nothing; a large city would lose simulation speed (not measured: the test region has only the tutorial cities).

Not changed: the loop never sleeps, so the game keeps a CPU core busy even when paused, as with the stock driver. Lowering that means changing the framework loop (for example waiting when paused), not the driver. Smoother motion while the simulation runs would need the simulation and drawing taken apart, which is far beyond the renderer.

### What the game asks the driver

The game configures itself from `Graphics Rules.sgr` (in the install folder), evaluated against values it collects at startup (0x007CF780): `textureStages`, `DXT`, the driver and card strings, memory, CPU speed and so on. The rules then decide, among other things, whether shadows use a second texture stage (`useSecondStage`, rule "Two stages": at least 2 stages), texture depth (`texturebits`, 16 under "No DXT"), the recommended shadow, effects and traffic levels ("Fast card": card names such as `NVidia*Geforce*`) and dirty-rectangle merging. Two driver calls feed it:

- **`GetVideoModeInfo` for the current mode.** Beyond the size and masks, `sGDMode` carries capabilities (field names from gzcom-dll's `sGDMode.h`): stencil (0x21), texture stage count (0x24), multitexture, texture env combine, NV combine4 and fog coordinate support (0x28-0x2B), DXT support (0x2C) and an initialised flag (0x30). The DirectX driver fills them only in the current mode; on this machine it reports 8 stages, multitexture, combine, fog coordinates, DXT and stencil, no combine4, an alpha mask of 0 for 32-bit modes, and 1 in the unknown bytes 0x22 and 0x2F.
- **`GetDriverInfo`.** Newline-separated: `Maxis 3D GDriver`, then sglDriverName, sglDriverVersion, driverName, driverVersion, cardName and cardVersion (the DirectX driver: `DirectX`, `2.0`, the display driver DLL, its version and device GUID, the adapter name, `Vendor: 10de, Device: 2208, Board: 153510de, Chipset: 00a1`).

Our driver first reported 1 texture stage, no DXT and empty strings (the mode fields had been copied from the OpenGL driver's list without being decoded). The game then left out the second shadow stage and drew shadows on models in a separate pass, which produced the halo, chose 16-bit textures and lower recommended settings. It now reports what the DirectX driver reports, with the real adapter from DXGI and `DirectX` as sglDriverName (what the rules were tuned on), and only the driver name and version lines name OpenSC4. **To check:** run the game with `-writeLog:on` (for example `OPENSC4_GAME_ARGS=-writeLog:on`): it writes `<computer name>-config-log.txt` next to the exe with every collected value and every rule applied. With either driver the logs now differ only in those two lines.

`diagnostics.d3d7_probe` ([d3d7_probe.cpp](../src/core/d3d7_probe.cpp)), used with the stock driver, logs the Direct3D 7 state the DirectX driver actually sets on its draws (render states, texture stage states, material, texture surface format), its `GetDriverInfo` and its mode records: the ground truth when our driver and the stock one disagree.
