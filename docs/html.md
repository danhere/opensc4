# HTML viewer

The HTML control the game uses for advice, news and the text pages, at 0x008F673E to 0x0090AD25: a COM director, the `HTML Window` class, a document that tokenizes and parses the page into a tree of nodes, the nodes' layout and paint, and under them an Internet service with a cookie store and a file cache that the game's pages hardly touch. It is the "HTML viewer" line of [uncharted-code.md](uncharted-code.md) and the "HTML parser" line of [framework.md](framework.md); the code starts a little below 0x008F6800 (the director), and 0x0090AD26 to 0x0090B1A0 belongs to the picture codecs, not to the viewer.

Everything here was read from the disassembly; the parser (h3), the layout (h4 and the layout side of h5), the nodes' paint and hit tests (h5b) the rest of h5's nodes, colours, character helpers, pictures and children (h5c, h5d) and the first half of h2, the document's node constructors and destructors, attribute setters, small tag handlers and tokenizer helpers (h2a), are ours and were checked in the game ("Ours: the parser", "Ours: the layout", "Ours: paint and hit tests", "Ours: nodes, colours and characters" and "Ours: the document's nodes, handlers and tokenizer helpers" below). Names are ours. The addresses the doc relies on are in [data/addresses/html.toml](../data/addresses/html.toml) (hooked only by the groups below) and [data/names-641.txt](../data/names-641.txt). "Ran" counts a function that ran in at least one of the 46 coverage files on TurboToaster (`%LOCALAPPDATA%\opensc4\analysis`, the `*coverage*.csv` and `cov.csv` files; [dev-environment.md](dev-environment.md), "Coverage"); code that runs only while the game starts is never recorded there.

## Library or Maxis

Maxis. There are no vendor or copyright strings in the range or in its data (0x00ACCC00 to 0x00ACE5A0), and the code is the framework's: packed (not aligned to 16 bytes), COM classes with `cRZCOMDllDirector` registration, `cRZString`, `cRZFile`, the STL allocator at 0x0090CF54. The parser's debug names (`ParseTABLE`, `ParseIMG`, `ParseFONT` and the rest, one per tag handler) and `Maxis Network Cache\` point the same way. So the whole viewer counts as Maxis code: nothing changes in `tools/progress.py` (`NOT_MAXIS`) or in the third-party line of [uncharted-code.md](uncharted-code.md).

## The parser

The tag table (0x00902D4F, built once into the hash map at 0x00B624A4) maps 160 names to IDs, each start and end tag its own ID (`!DOCTYPE` 2, `HTML` 4, `BODY` 8, `FONT` 0x20, `A` 0x36, `IMG` 0x38, `BR` 0x3B, `P` 0x65, `TABLE` 0x78, `TD` 0x8F, `TR` 0x93, `NOBR` 0xA1). The tokenizer is three functions on the document: 0x008FFAC2 collects text up to the next `<`, skipping `<!-- -->`; 0x00905CF0 reads the next tag and looks its name up (the current ID at +0xE8); 0x009056DA splits its attributes (quoted with `"` or `'`, or bare). Colours go through 0x0090AA54: `#rrggbb` or the 16 HTML colour names.

Parsing is recursive descent. 0x00908122 (document slot 8) starts it: it checks `<!DOCTYPE ... DTD HTML x.y>` (slot 9, 0x008FFF91) and runs 0x009080A2, which makes the body node and calls 0x00907E42 for `BODY`; text that does not start with a tag becomes one plain text run (slot 11, 0x00905985). From there 0x00907135 handles block tags (HR, P, PRE, DL, DIV, BLOCKQUOTE, FORM, TABLE, CENTER, headings, lists; NOSCRIPT, FIELDSET, ADDRESS, DIR and MENU are skipped to their end tag by 0x009065C5) and 0x00907CCA handles text and inline tags: text (ID 3) becomes a text node (0x008FE6E2), and four tag sets go to 0x0090727D (font tags: TT, I, B, U, STRIKE, BIG, SMALL, FONT), 0x00906985 (phrase tags), 0x00907C3E (A, IMG, BR, SCRIPT, MAP, SPAN, BLINK; OBJECT, Q, SUB, SUP, BDO skipped to their end tag) and 0x00906E59 (INPUT, SELECT; TEXTAREA, LABEL, BUTTON skipped).

Images are asked for while parsing: the document's slot 16 (0x009059FC) gives a node the picture of an address already in the image map (+0x198), or queues the node and asks the Internet service (its slot 17) for a new address; 0x008FFBFC reads an image that arrives (`cRZFile` and the picture reader) and hands it to the nodes waiting for it. Named entities are decoded by the text node's constructor through 0x00901222, which fills each document's own entity map (a tree at +8) on first use.

Still the game's: the rest of h2 (image fetching, the document's slots; h2a's tokenizer helpers, small handlers, attribute setters and node constructors are ours in groups of their own, "Ours: the document's nodes, handlers and tokenizer helpers") and every STLport and string helper. Kept as the game has them:

- Attributes: the character after an opening quote is always taken, so `a=""` takes the closing quote and reads on to the next one; a quote never closed runs to the tag's end; a name in quotes loses them, names are upper-cased and empty names dropped; a tag's attributes last until the next tag.
- FONT's SIZE: `+n` and a plain number are capped at the seventh step but not kept from going below the first, `-n` the other way round, so `SIZE=+-9` reads a "step" from before the table. A font tag's handler reached with an ID it does not know returns false with the font still pushed (the dispatch never sends one).
- SPAN's `font-size` looks for `px` or `pt` in the key, not in the value, so it never sets a size; it only puts a size of 0 or above 255 back to 14.
- Tables: the parts are read in the order THEAD, TFOOT, TBODY, so a TFOOT after a TBODY is skipped with the rest of the table; COLGROUP gives back its end tag, which ends the table's parts the same way; TH cells are the row's children but not in its cell list (+0x28); a row's VALIGN is not read.
- Nesting: a tag closed out of order (`<B><I></B></I>`) makes the inner handler skip to its own end tag and the outer one to its, which may be past the end of the page: the rest of the page is lost.
- Lists: the depth counters (+0x128 for OL, +0x12C for UL) count every list the document ever made, never down.
- The colour maker (slot 34 of 0x00913C1A) gets red, green and blue as the dwords the game finds at those bytes of its stack; it reads only the low byte of each (0x00825DA0), so ours pass them clean.

How it works. The context (0x68 bytes; the window's at +0xE0) has the window's client rectangle (+0xC) and the part of the page in view (+0x1C), the line's height (+0x2C) and ascent (+0x30), the pen (+0x34, +0x38), the left margin (+0x40), the left margin of the lines after this one (+0x44) and the right margin (+0x48), a list of line items waiting (+0x4C), and the left and right entries (+0x50, 16 bytes: a flag for a float, its bottom, the margins it covers; +0x5C, 8 bytes: bottom and margin). Nodes put items on the line (text runs and images in the line); a block flushes the line before and after it. Flushing measures the items against the width between the margins (each item's slot 1 for height and ascent, slot 2 for how much fits), and while the line is full (or always, when asked) aligns it by its last item (slot 0: left, centre, right), places the items (slot 3) until the pen reaches the right margin and goes to the next line, the line's height below; NewLine ends the floats whose bottom the line has reached. A text run breaks at spaces (FitString, font slot 41); a piece of a line is 24 bytes (box, start, count) in the run's vector at +0x4C, its box without the spaces at its end. The window lays the body out (slot 3), then the second pass (slot 4) makes each container's box the union of its children's.

A table (0x0090A448) starts at the pen, after a flush. Its columns are as many as the most TD cells of a row (+0x28 of each row; TH cells are not among them and are never laid out), each 0x1C bytes at +0x70: its narrowest, its widest, the most and least of its fixed widths, its narrowest when the widths were last shared, its left and its slack (widest less narrowest); one more column's left is the table's right. The rows' heights are at +0x7C and their tops at +0x88 (one more). The row's cells (0x00909FF2) are each laid out in a copy of the context. A first pass measures: each cell's Layout (slot 3, TD's 0x0090A34F) at the pen, its box giving the row's height and the column's widest; a cell with a width in pixels (+0x2C 0, the width at +0x30) is laid out between margins at the page's left and that width (floats that never end), and its box gives the column's narrowest too. Then each column gets its narrowest and a share of the width between the margins left over, by its slack (`(slack * left + slack left - 1) / slack left`, from the first column on); the rows are laid out in place (each cell between its column's left and the next one's, from the row's top), a cell wider than its column making the column's narrowest that, and while some column's narrowest grew, the widths are shared again and the rows again. When the narrowest together are more than the width, or no column has slack, the widths are not shared at all. Last, the heights start from nothing, the rows are laid out in place once more for them, the tops are made again from the table's top, and each row is laid out in place a final time with the pen's line at its top, the cells by 0x00909837 into the rectangle of their column and row; the pen's line is left at the table's bottom (its x as it was), and the table's box is the columns' left and right and the rows' top and bottom.

Kept as the game has them:

- The start of a layout puts the pen's x at the client rectangle's left, not less the scroll position as the margins are; a line aligned left, centre or right sets the pen from the margin anyway.
- The text item's ascent is the font's slot 38, but never more than the line height (the larger of slots 35 and 37); the line's height and ascent are the most of its items' each, from different items.
- An image's width is compared unsigned with the width left, so on a line whose width left is below 0 an image fits. An image with no WIDTH or HEIGHT is laid out as nothing.
- HR's WIDTH as a percentage is of the margins' width less 10, after SIZE is made at least 1, WIDTH at least 0 and a percentage at most 100; the next line is SIZE + 10 below the pen's line, the rule 5 pixels in from the pen.
- A numbered item's number (vtable 0x00ACD7A0) only sets the hanging indent: the lines after it start where the items waiting end. Its own children are never laid out.
- The left entries of indents and floats share a stack: NewLine ends floats only down to the first indent, Unindent ends whatever is last.
- The spaces at a piece's end are found with the character helper counting from the string's start but read from the piece's start; the same for one-byte text.
- TD's Layout makes the second pass itself, then clears the box and makes it again from its children; a cell's +0x30 is read only when +0x2C is 0, and is whatever the heap had otherwise.
- Tables: BORDER, WIDTH, CELLPADDING and CELLSPACING are read by the parser and never by the layout, nor a cell's width in percent, COLSPAN or ROWSPAN. A cell's width in pixels counts only in the first pass, laid out at the page's left (not the pen's) on the pen's line; the most and least of a column's fixed widths (+8, +0xC) are kept and never read. The width the columns share is the margins' width compared with itself (the compiler's leftover of a smaller-of). A column's widest grown (0x00909A6D) is made at least its narrowest, which the narrowest's own growing (0x00909A47) already keeps: to no effect.

Not as the game has it: an indent's bottom. The game leaves it as its stack has it; it is read only when nothing of a line's first item fits (a word longer than an indented line): at 0x3FFFFFFF or above, the item is forced onto the line as it is outside lists; below, the line gets an empty piece and the flush goes on to the next line. With the groups off, a layout test run with a page of lists nested past the page's width did not get through that page (the game ended); through the detours, the stack held a value above and the words were forced. Ours puts 0x3FFFFFFF there, so such a word is always forced. The test's pages keep out of that case; a list in a table cell beside floating images was one more such page (the game alone did not get through it).
